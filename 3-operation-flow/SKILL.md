基于前两份文档，生成一份完整的测试操作文档。**以功能模块（M-XX）为单位组织测试集**，每个功能模块对应一个独立文件，一个文件就是一个完整的测试集。人类测试人员可以按此文档逐步执行测试，覆盖该功能的所有场景。每个步骤以结构化列表格式呈现，包含导航路径（涉及页面操作时）、操作动作、详细后端逻辑。

---

**前置条件**：
- `magic-align-spec/1-tech-implementation-plan/overview.md` 必须已生成
- `magic-align-spec/2-detailed-design/overview.md` 必须已生成

**输入**（二选一）：
- **文档模式**：前两份文档 + 需求文档/PRD
- **代码分析模式**：分析现有项目代码，从代码中提取操作流程和 API 调用链路。需要用户确认后才执行代码分析

**输出**：测试操作文档（Markdown 格式），按功能模块拆分为多个文件，写入当前项目目录的 `magic-align-spec/3-operation-flow/` 目录下：

```
magic-align-spec/3-operation-flow/
├── overview.md                    # 文档信息、测试环境准备、测试数据清理
├── M-01-<功能名>-operation.md     # M-01 功能模块的完整测试集（管理后台 + 外部应用 + 系统自动行为）
├── M-02-<功能名>-operation.md     # M-02 功能模块的完整测试集
└── ...
```

- **一个功能模块（M-XX） = 一个测试集（一个文件）**，与详细设计文档的 M-XX 一一对应
- 如果一个功能模块内部可以拆分为多个子模块（比如"用户管理"拆为"用户信息管理"和"用户权限管理"），**不拆文件，只在文件内增加 `####` 层级来区隔子模块**
- `overview.md` 包含文档信息、测试环境准备、测试数据清理
- 每个 `M-XX-<功能名>-operation.md` 包含该功能模块所有测试场景和操作步骤
- 一个功能模块内部按操作入口分为多个测试场景（管理后台操作、外部应用操作、系统自动行为），都放在同一个文件中

---

## 执行步骤

### 1. 前置检查

依次检查两份前置文档，缺失则告知用户先生成对应文档。

### 2. 技术方案确认状态检查

读取 `magic-align-spec/1-tech-implementation-plan/` 目录下 overview.md 中每个技术方案（T-XX）的"确认状态"字段：

- **全部已确认**：正常继续
- **存在待确认或存疑的方案**：使用 **AskUserQuestion** 逐项向用户确认：
  - 待确认的方案：询问"T-XX {方案名称} 的技术选型 {当前选型} 是否确认？如有调整请说明"
  - 存疑的方案：询问"T-XX {方案名称} 当前存疑，原因：{存疑原因}。请确认最终方案或提供替代方案"
  - 根据用户回复，**更新 `magic-align-spec/1-tech-implementation-plan/` 目录下对应方案文件** 中对应方案的确认状态
- 确认完成后继续执行

### 3. 确认输入来源

向用户确认输入方式：

- **文档模式**：直接使用前两份文档和需求文档/PRD
- **代码分析模式**：如果用户选择分析代码，先扫描项目代码中的路由定义、API 控制器、中间件，提取操作流程和 API 调用链路。分析前向用户说明分析范围和将要检查的文件

### 4. 按功能模块梳理测试场景

从详细设计文档中读取所有 M-XX 功能模块，**为每个 M-XX 建立一个独立的测试集**，再在该测试集内部按操作入口分类梳理测试场景：

- **管理后台操作**：运营人员在 Web 页面的操作（增删改查、上传、配置等）
- **外部应用操作**：用户在外部应用（企业微信等）的操作（发消息、发文件等）
- **系统自动行为**：系统在特定条件下自动执行的操作（同步、联动、回调等）

如果一个功能模块的业务范围较大，可以拆分为多个**子模块**（如"工单管理"下有"工单创建"、"工单审批流转"、"工单归档"三个子模块），此时：

- **不拆文件**，所有子模块的测试场景仍在同一个 M-XX-operation.md 中
- 子模块用 `####` 标题层级区隔（比 `#####` 场景标题高一级），在每个操作入口分类内部按子模块分组
- 子模块不改变编号体系，依然使用 `OP-M-XX.{场景}.{步骤}`，但用标题明确标示当前所属子模块

一个功能模块也可能没有子模块，直接按操作入口分类组织即可。

### 5. 编写测试步骤

每个测试场景下的步骤以结构化列表格式逐一罗列，每个步骤包含以下字段：

- **编号**：唯一操作编号，格式 `OP-M-XX.{场景}.{步骤}`，其中 M-XX 与功能模块编号一致，确保可追溯到详细设计
- **步骤**：该步骤在场景中的序号
- **导航路径**：该操作在网页中的导航路径，如"设置 tab → 服务器管理页面 → 新增弹窗"（非页面操作可省略，如系统自动行为）
- **操作**：用户执行的具体动作（点击按钮、填写字段、发送消息等），只描述影响后端的动作
- **后端逻辑**：该操作对应的后端处理逻辑，按调用顺序分点罗列（1. 2. 3.），内容包括接口调用、参数校验、数据变更、事务处理、外部调用等
- **代码实现**：标记实现状态（未实现/已实现）

### 6. 输出

将文档按功能模块拆分为多个文件，写入 `magic-align-spec/3-operation-flow/` 目录：

1. 先写 `overview.md`，包含文档信息、测试环境准备、测试数据清理
2. 再按 M-XX 编号顺序逐模块写 `M-XX-<功能名>-operation.md`，每个文件包含该功能模块的所有测试场景和操作步骤

## 编写原则

- **一个功能模块一个测试集**：每个 M-XX 功能模块对应一个独立的测试文件，与详细设计文档的 M-XX 一一对应。不跨模块合并，也不在一个模块内混入其他模块的测试场景
- **子模块层级不拆文件**：如果一个功能模块可以拆分为多个子模块，**不在文件层面拆分**，而是在文件内用 `####` 标题区隔子模块。保持"一个 M-XX = 一个文件"的原则不变
- **列表格式**：每个步骤以结构化列表格式逐一罗列（编号、步骤、导航路径、操作、后端逻辑、代码实现），不使用表格
- **导航路径**：涉及页面操作的步骤必须描述导航路径（如"设置 tab → 服务器管理页面 → 新增弹窗"），方便测试人员快速定位。系统自动行为等非页面操作可省略
- **可执行**：测试人员拿到文档就能按步骤操作，每一步是单一动作（点击按钮、填写字段、发送消息等）
- **后端逻辑分点详述**：后端逻辑按调用顺序分点罗列（1. 2. 3.），内容包括接口调用、参数校验、数据变更、事务处理、外部调用等，不说"调用了 XX 接口"就结束
- **只写影响后端的操作**：不影响后端的步骤（如弹窗打开、纯前端校验提示）不描述
- **覆盖完整**：一个功能模块内，管理后台操作、外部应用操作、系统自动行为三类场景都要覆盖，确保测试人员能走完该功能的完整业务流程
- **引用上游**：功能模块编号（M-XX）和技术方案编号（T-XX）与前两份文档保持一致
- **代码实现标记**：每个操作步骤默认标记为"未实现"，由技能 6 实现后更新为"已实现"
- **按功能模块拆分文件**：每个 M-XX 一个独立测试集文件，overview.md 放环境准备和清理
