# 「岗位Agent管理后台 — Agent 管理」PRD

## 1\. 需求背景

当前 Agent（企微机器人）的管理分散在不同系统中，缺乏统一的管理后台。需要将 Agent 管理收拢到**统一管理后台**，实现 Agent 配置、状态管理、渠道活码管理、官网配置的单系统闭环，支撑官网自动同步展示。

## 2\. 需求价值

- **统一管理入口**：运营人员在一个系统内完成所有 Agent 的配置和状态管理，减少跨系统操作成本

- **自动化官网同步**：后台配置直接驱动官网展示，避免手动维护导致的信息不一致

- **Agent 能力可视化**：通过 Skill 目录和能力绑定，让每个 Agent 能提供什么服务一目了然

## 3\. 期望结果

1. 运营人员可在后台新增、查看、编辑、停用所有 Agent

2. 每个 Agent 可绑定 Skill 列表，并以自然语言描述其任务处理能力

3. Agent 上架后，官网配置页面可选择该 Agent 并配置展示素材

4. Agent 停用后，后续新建群不再包含该 Agent 的企微员工，官网同步隐藏，已关联的群不受影响

5. 管家 Agent 作为路由调度核心，固定存在，不可删除

### 4\.3 Agent 状态管理

**状态机**：

```Plain Text
[停用] <--- (停用操作) --- [已上架]
[停用] --- (上架操作) ---> [已上架]

















```

|状态|含义|可执行操作|不可执行操作|
|---|---|---|---|
|已上架|Agent 正常运营中|停用、编辑|—|
|已停用|Agent 已下线|上架、编辑|—|

**管家 Agent 特殊规则**：

- 固定上架，不可停用

- 固定存在，不可删除**状态变更影响**：

|变更|影响范围|
|---|---|
|上架 \-\&gt; 停用|官网同步隐藏该 Agent（**保留配置，不删除**）；后续新建群**不再包含**该 Agent 的企微员工；已建好的群中该员工正常退出；管家Agent始终在群中不受影响|
|停用 \-\&gt; 上架|官网可选择该 Agent 进行配置，**原展示配置自动恢复**（素材、话术、排序、状态均保留）；后续新建群**重新包含**该 Agent 的企微员工|

**说明**：每次建群时**实时查询**当前岗位上架 Agent 的企微员工列表，不存在固定\&\#34;群模板\&\#34;实体。无论多少个 Agent 停用，管家 Agent 始终跟随岗位角色在所有群中。

### 4\.7 管家Agent 路由与意图识别机制

> 本节定义管家 Agent 的路由分发规则、会话记忆模型、典型交互场景和异常处理策略。

#### 4\.7\.1 基础概念定义

|概念|说明|
|---|---|
|**管家Agent（交付总监）**|群内所有消息的唯一入口，负责意图识别和路由分发，不做具体业务回复|
|**专业 Agent**|负责具体业务处理的 Agent（产品经理Agent、架构师Agent、工程师Agent、QAAgent 等），每个 Agent 绑定一个独立的企微员工|
|会话|`session\_key = user\_id \+ agent\_id`。按用户×Agent 维度拆分，互不干扰|
|会话超时|30 分钟无交互后，短期记忆清理。超时的会话不丢失上下文，恢复时提供摘要|
|路由模式|**网关转发**。管家Agent 识别意图后调用目标 Agent，目标 Agent 用自己的企微员工在群里直接回复|

**话术规范**：管家Agent 所有转交提示统一使用「收到，已转交给XXX处理。」无需多余说明，避免刷屏。**用户感知层**：管家Agent 拦截过程对用户完全无感知。用户发送消息后，直接收到目标 Agent 的回复（或转交提示），中间不可见管家Agent 的操作。

#### 4\.7\.2 统一路由原则

**所有消息 → 管家Agent 拦截 → 管家Agent 说了算。管家Agent 意图匹配机制：管家Agent 捕获群消息后，先加载当前群内所有已上架 Agent 的Agent 描述文本**（自然语言），然后将用户消息与各 Agent 描述进行语义匹配，确定最合适的处理 Agent。Agent 描述同时用于：

10. **运行时路由**：作为管家Agent 意图匹配的参考语料

11. **兜底话术**：汇总各 Agent 描述，自动生成群的工作范围概要**规则一：用户 @了某个 Agent**

- 匹配 Agent 能力范围 → 将消息\+附件传入该 Agent 上下文处理

- 不匹配 → \&\#34;这事应该由XXX处理，是否转交？\&\#34;

    - 用户确认转交 → 路由目标 Agent

    - 用户拒绝 → 保持原 Agent 处理

    - 用户未回复（超时 60s）→ 不做转交，保持原 Agent 处理示例：

- 用户 @产品经理Agent \&\#34;写个PRD\&\#34; → 匹配，直接转发

- 用户 @产品经理Agent \&\#34;数据库表怎么设计\&\#34; → 不匹配，提示\&\#34;这事应该由架构师处理，是否转交？\&\#34;

- 用户 @工程师Agent \&\#34;这个需求能实现吗\&\#34; → 不匹配（需求分析归产品经理），提示\&\#34;这事应该由产品经理处理，是否转交？\&\#34;**规则二：用户没 @任何人**管家Agent 自由分配，不问用户。

|场景|管家Agent 行为|传给 Agent 的内容|
|---|---|---|
|有活跃会话 \+ 消息是当前话题延续|继续给当前 Agent|当前消息 \+ 附件 \+ 该 Agent 的完整对话上下文|
|有活跃会话 \+ 消息跨越 Agent 领域|直接转交，「已转交给XXX处理」|当前消息 \+ 附件 \+ 原 Agent 会话摘要|
|无活跃会话|语义判断→路由到合适 Agent|当前消息 \+ 附件|
|发图/发文件|追问\&\#34;请告诉我您想做什么\&\#34;|—|
|模糊/无法回答|引导或兜底回复|—|

**规则三：唯一需要问用户的情况**只有两种场景需要跟用户确认：

12. **用户 @了A，但消息实际上是B的事** → \&\#34;这事应该由B处理，是否转交？\&\#34;

13. **用户发图/发文件** → 追问\&\#34;请问这是给当前方案做补充，还是有新的需求需要处理？\&\#34;其余一切场景，管家Agent 直接判断、直接路由、直接分配。

#### 4\.7\.3 会话与记忆模型

**两层记忆架构**：

|维度|短期记忆（Agent 内存）|长期记忆（Agent 本地存储）|
|---|---|---|
|存什么|对话全文（用户消息\+Agent回复\+附件）|已确认的结论、用户偏好、用户角色|
|更新方式|每次对话自动追加|Agent 回复后自动提取|
|清理条件|30分钟无交互|不清理（除非用户要求删除）|
|转交时|生成摘要传给目标 Agent|不传（各 Agent 自管）|

\*\*短期记忆（Agent 内存）\*\*每个 Agent 在内存中维护 `user\_short\_term\_memory\[user\_id\]`，存对话全文，30分钟无交互后清理。转交时生成会话摘要传给目标 Agent。存储结构示例：

```JSON
{
  "user_id": "user_A",
  "agent_id": "产品经理Agent",
  "last_active": "2026-05-14 15:00:00",
  "rounds": [
    {"role": "user", "content": "帮我写个日报收集的PRD", "attachments": []},
    {"role": "agent", "content": "好的，以下是日报收集功能的PRD框架...", "summary": "已输出日报PRD框架"}
  ],
  "session_summary": "用户需要日报收集功能，含日期/内容/状态三个字段，产品经理已出方案框架"
}

















```

\*\*长期记忆（Agent 本地存储）\*\*每个 Agent 本地维护 `user\_long\_term\_memory\[user\_id\]`，存 3 类结构化信息：**1️⃣ 历史对话结论**定义：用户与该 Agent 在历史对话中明确确认过的方案、决策、选择。提取时机：Agent 每次回复后，判断是否输出结论性内容。提取提示词：

```Plain Text
请从当前对话中提取结论性信息：
- 用户确认了什么方案？
- 选定了什么技术/工具/方法？
- 同意或否定了什么？
- 约定下一步做什么？

如果没有明确的结论，返回空。
格式：["结论1", "结论2", ...]

















```

存储示例：

```JSON
{
  "conclusions": [
    "用户确认日报收集功能用PostgreSQL数据库",
    "字段包含：日期、内容、状态、审批人",
    "不采用Elasticsearch方案，太复杂了"
  ]
}

















```

**2️⃣ 用户个人偏好**定义：用户在跟该 Agent 沟通过程中，表达出来的喜好和风格倾向。提取时机：对话过程中，尤其是用户对 Agent 输出给出反馈时。提取提示词：

```Plain Text
从当前对话中分析用户的个人偏好：
- 用户对回复风格有什么要求？（简洁/详细/带例子/带图）
- 用户喜欢/不喜欢什么做事方式？
- 用户对某些方案有明显的倾向性吗？
- 用户的沟通习惯？

如果没有明显的偏好，返回空。
格式：{"风格偏好": "...", "做事方式": "...", "其他偏好": "..."}

















```

存储示例：

```JSON
{
  "preferences": {
    "回复风格": "偏好简洁，两步内给结论，不要长篇分析",
    "做事方式": "喜欢先看框架再决定是否深入",
    "其他": "不接受技术黑话，需要用业务语言解释"
  }
}

















```

**3️⃣ 用户角色信息**定义：用户告诉过 Agent 自己的身份和上下文。提取时机：用户自我介绍或主动提示时。提取提示词：

```Plain Text
从当前对话中提取用户角色信息：
- 用户的职位/角色是什么？
- 用户所属部门或团队？
- 用户当前负责什么项目？
- 用户在团队中的决策权限（决策者/执行者/建议者）？

如果没有明确信息，返回空。
格式：{"角色": "...", "部门/团队": "...", "项目": "...", "决策权限": "..."}

















```

存储示例：

```JSON
{
  "role": {
    "职位": "产品经理",
    "团队": "CRM产品组",
    "项目": "岗位Agent管理后台",
    "决策权限": "建议者，最终需总监确认"
  }
}

















```

**长期记忆约束规则**：只存明确可结构化的信息，不存模糊/推测/不确定的内容。宁可漏存，也不要存错存乱。各 Agent 的长期记忆互不共享，由各 Agent 自管自用。**长期记忆的用户管理能力**（作为 Agent 的默认能力）：

|用户操作|Agent 响应|说明|
|---|---|---|
|查看长期记忆|Agent 读出结构化摘要回复用户|用户主动询问\&\#34;你还记得关于我的什么信息\&\#34;时触发|
|删除全部记忆|Agent 清除该用户的全部长期记忆|用户要求\&\#34;删除我的所有记录\&\#34;时执行|
|删除单条记忆|Agent 定位并删除指定条目|用户要求\&\#34;删除其中某条\&\#34;时执行|
|纠错|Agent 更新指定条目的内容|用户指出记忆错误时更正|
