从全局视角描述项目的一整套技术方案，每个方案是一个完整的组件（如一个网站、一个调度器、一个 Windows 服务等），说明其实现目标。同时描述功能模块级别的需求覆盖。

---

**输入**（二选一）：
- **文档模式**：用户传入需求文档/PRD 引用，或直接描述项目背景和需求概述
- **代码分析模式**：分析现有项目代码，逆向推导技术方案。需要用户确认后才执行代码分析

**输出**：技术方案设计文档（Markdown 格式），按方案拆分为多个文件，写入当前项目目录的 `magic-align-spec/1-tech-implementation-plan/` 目录下：

```
magic-align-spec/1-tech-implementation-plan/
├── overview.md              # 总览：文档信息、方案总览表、方案间交互关系、项目文件夹结构
├── T-01-<方案英文名>.md      # 单个技术方案的详细说明（技术栈、覆盖模块、方案说明）
├── T-02-<方案英文名>.md
└── ...
```

- `overview.md` 包含全局信息（方案总览表、交互关系、文件夹结构）
- 每个 `T-XX-<方案英文名>.md` 包含该方案的详细技术设计
- 新增方案时追加新的 T-XX 文件，修改方案时只更新对应文件

## 执行步骤

### 1. 确认输入来源

向用户确认输入方式：

- 如果用户传入了需求文档/PRD：进入文档模式，读取文档内容
- 如果用户未提供文档：使用 **AskUserQuestion** 询问：
  - 是否有需求文档/PRD？
  - 是否需要分析现有项目代码？（需要用户明确确认）
  - 项目名称和简介
  - 已知的约束条件（时间、人力、基础设施等）

**代码分析模式**：用户确认后，先整体扫描项目代码结构（目录、package.json/go.mod/pom.xml 等配置文件、主要模块入口），识别已有的技术组件和交互关系，再生成技术方案。分析前向用户说明分析范围和将要检查的文件。

### 2. 编写技术方案

按以下流程逐方案、逐维度与用户确认：

1. 先列出识别出的所有技术方案（T-XX），让用户确认方案划分是否合理
2. 对每个 T-XX，逐维度使用 **AskUserQuestion** 向用户确认：

   **五个必问维度**：
   - **前端技术**：框架、构建工具、UI 组件库、状态管理等。纯后端服务跳过
   - **后端技术**：语言、Web 框架、ORM、中间件等
   - **数据库技术**：关系型数据库、NoSQL、搜索引擎等。无需持久化的方案跳过
   - **缓存技术**：Redis/Memcached 等。无缓存需求的方案跳过
   - **部署方案**：容器化方式、反向代理、CI/CD、运行环境等。Docker 部署的方案须确认日志挂载（`logs/` 目录挂载到容器内）

   每个维度询问时：
   - 给出推荐选型和理由
   - 列出备选方案供用户参考
   - 让用户确认或指定其他选型

3. 用户确认一个维度后，立即更新文档中对应维度的确认状态为"已确认"
4. 所有 T-XX 的所有维度确认完毕后，进入输出步骤

**确认顺序**：先确认所有 T-XX 的划分 → 再逐 T-XX 确认其各维度 → 最后确认方案间交互关系

### 2.1 确认项目文件夹结构

所有技术方案的维度确认完毕后，使用 **AskUserQuestion** 询问用户：

> 是否使用默认文件夹模板创建项目结构？

- **使用默认模板**：根据各方案的技术栈选型，直接套用下文「默认文件夹模板」中的结构，填充到 overview.md 的项目文件夹结构章节。模板已覆盖的目录无需重复设计，仅需根据实际功能模块补充业务目录
- **自定义结构**：与用户逐方案讨论目录结构，按用户意愿定制

默认模板覆盖以下方案类型：
- 前端 Web 应用（React/Vue + TypeScript）
- Python 后端服务（FastAPI/Flask）
- 其他方案类型（Go 后端、定时调度器等）暂提供通用结构，后续按需补充

### 3. 输出

将文档按方案拆分为多个文件，写入 `magic-align-spec/1-tech-implementation-plan/` 目录：

1. 先写 `overview.md`，包含文档信息、方案总览表、方案间交互关系、项目文件夹结构
2. 再逐方案写 `T-XX-<方案英文名>.md`，每个文件包含该方案的详细说明
3. 列出需要用户确认的关键决策点

#### 2. 技术方案总览

列出项目所需的整套技术方案。每个方案是一个独立的、可交付的组件，分配唯一标号 `T-XX`。

| 编号 | 方案名称 | 实现目标 | 技术栈摘要 | 确认状态 | 详细文件 |
|------|---------|---------|-----------|---------|---------|
| T-01 | 基础网站 | 提供用户操作界面，实现 xxx 功能 | React + Go + PostgreSQL + Redis + Docker | 待确认 | T-01-web-app.md |
| T-02 | 后台调度器 | 定时执行 xxx 任务，处理 xxx | Python + Celery + Redis + Docker | 待确认 | T-02-scheduler.md |
| T-03 | Windows 服务 | 常驻后台，监听 xxx 并执行 xxx | .NET + SQLite | 待确认 | T-03-windows-service.md |

**确认状态**：`待确认` / `已确认` / `存疑`。由各技术维度的确认状态综合决定：全部已确认则为已确认，任一存疑则为存疑，其余为待确认。生成时逐维度向用户确认，用户跳过的维度保留"待确认"。

#### 3. 方案间交互关系

描述各技术方案之间的交互方式和数据流转。每个交互关系说明方案 A 通过什么方式与方案 B 通信。

| 交互编号 | 方案 A | 方案 B | 交互方式 | 说明 |
|---------|--------|--------|---------|------|
| I-01 | T-01 前端应用 | T-02 后端服务 | HTTP REST API | 前端所有操作通过 API 与后端交互 |
| I-02 | T-02 后端服务 | T-03 数据库 | ORM / SQL | 后端通过 ORM 读写业务数据 |

**交互方式**可选：HTTP REST API、HTTP 回调、内部 RPC（gRPC/tRPC）、消息队列（RabbitMQ/Kafka）、共享数据库（读写同一库表）、SDK 调用、WebSocket

**编写原则**：
- 只描述方案之间存在交互的关系，没有交互的不需要列出
- 交互方式要具体，不要写"接口"这种模糊表述
- 说明要一句话讲清楚交互的目的和数据流向

## 编写原则

- **方案即组件**：每个技术方案是一个完整的、可独立交付的组件，而非通用技术层次
- **目标驱动**：先说清楚这个方案要解决什么问题，再说用什么技术
- **维度覆盖**：每个 T-XX 至少确认前端技术、后端技术、数据库技术、缓存技术、部署方案五个维度。不适用的维度标注"不适用"并说明原因
- **逐维度确认**：每个技术维度的选型单独确认，最终方案确认状态由各维度综合决定
- **标号化**：技术方案和功能模块均使用唯一编号，便于后续文档引用
- **可分配**：需求覆盖范围以 T-XX 为主体组织，每个 T-XX 是一个完整工作包，可直接分配给不同人独立开发。跨 T-XX 的功能模块标注"跨方案协作"
- **主动逐维确认**：生成文档时，每个 T-XX 的每个技术维度都通过 AskUserQuestion 逐一向用户确认，用户确认后才标记为"已确认"。不生成大量"待确认"后让用户自己改。后续文档生成前，会检查确认状态：全部已确认则继续，存在待确认或存疑的方案则中断并向用户确认，确认后更新本文档的确认状态再继续
- **文件夹结构只到目录级**：项目文件夹结构只展开到文件夹层级，配置文件名（如 package.json、.env）为方便识别可列出，但不展开源码文件
- **默认模板优先**：设计项目文件夹结构时，优先询问用户是否使用默认模板。模板覆盖前端和 Python 后端，用户确认后直接套用，仅需补充业务模块目录

## 实现约束

每个技术方案在实现时，以下内容统一遵循。

### Docker 日志挂载规范

所有使用 Docker 部署的方案，必须在容器配置中挂载日志目录：

- 宿主机项目根目录下创建 `logs/` 目录，用于集中存放所有方案的日志文件
- Docker Compose 中将 `logs/` 目录挂载到容器内的日志输出路径
- 方案内的日志框架统一输出到容器内挂载的日志目录，不输出到 stdout 以外的容器内部路径
- `logs/` 目录按方案分子目录，如 `logs/web-app/`、`logs/backend-service/`

示例（Docker Compose）：
```yaml
services:
  backend:
    volumes:
      - ./logs/backend-service:/app/logs
```

### Git 忽略规范

项目根目录的 `.gitignore` 必须包含以下规则：

```gitignore
# 日志文件
logs/

# 敏感配置
.env
```

`logs/` 目录下的所有日志文件不提交到代码仓库。

### 配置文件规范

每个方案必须将敏感配置与业务配置分离为两个文件：

| 文件 | 用途 | 是否提交 | 内容示例 |
|------|------|---------|---------|
| `.env` | 敏感/环境相关配置 | 不提交 | 密钥、数据库密码、第三方 API Key、用户信息 |
| `config.yaml` | 业务/应用配置 | 提交（不含敏感值） | 模型参数、API 地址、压缩策略、文件路径、日志级别 |

**Python 项目参考**：

`.env` 示例：
```bash
# 数据库
DB_HOST=127.0.0.1
DB_PORT=3306
DB_USER=admin
DB_PASSWORD=xxx
# 第三方密钥
OPENAI_API_KEY=sk-xxx
JWT_SECRET=xxx
```

`config.yaml` 示例（每个配置项必须附带注释说明作用、格式、范围和修改后果）：
```yaml
# ===== 服务配置 =====
server:
  host: "0.0.0.0"               # 监听地址，0.0.0.0=所有网卡，127.0.0.1=仅本机
  port: 8000                     # 监听端口，范围 1024-65535

# ===== 日志配置 =====
logging:
  level: "INFO"                  # 日志级别：DEBUG/INFO/WARN/ERROR，生产环境用 INFO 以上
  path: "./logs/backend-service/"  # 日志输出目录，Docker 部署时挂载到宿主机

# ===== 模型配置 =====
model:
  embedding: "text-embedding-3-small"  # Embedding 模型名，更换模型需确认向量维度一致
  temperature: 0.7                     # 生成温度，0-2，越高越随机，代码/逻辑类场景建议 0.3 以下

# ===== 外部 API 配置 =====
api:
  base_url: "https://api.openai.com/v1"  # API 基础地址，不要以 / 结尾
  timeout: 30                              # 请求超时（秒），超过 60 可能触发网关超时
```

**其他语言项目**遵循相同原则，使用该语言生态惯用的配置文件格式：
- Node.js/TypeScript：`.env` + `config.json` 或 `config.ts`
- Go：`.env` + `config.yaml`（使用 viper 等库）
- Java：`.env` + `application.yml`（Spring Boot）

> `.env` 文件必须加入 `.gitignore`，`config.yaml` 可提交但不得包含密钥、密码等敏感值。
