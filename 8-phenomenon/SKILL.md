用户描述界面上某个**不符合预期的现象**（如点击无反应、数据显示不对、流程走不通等），AI 按三层诊断链路判断问题归属，**明确告知用户属于哪类问题**，再执行对应处理。

**三种诊断结果与处理方式**：

| 诊断结果 | AI 做什么 | 需要用户确认？ |
|---------|----------|--------------|
| 使用方式问题 | 告知正确用法，不修改任何东西 | 否 |
| Bug（文档正确） | 直接修复代码 | 否 |
| 文档问题 | 展示变更计划 → 用户确认 → 只改文档 | **是** |

> 文档问题处理完后，代码由用户自行通过 `/magic-6-code-impl` 实现。

**特别注意**：8-phenomenon 修改的是 `magic-align-spec/` 下**已有的设计文档**（2-detailed-design、3-operation-flow、4-database-schema、5-api-spec），直接在原文上修正，不新增 CHG-XXX 变更编号，不追加变更记录。变更编号和变更记录是 `magic-7-req-change` 的职责。

---

**输入**：用户描述的现象。用户可能以任意形式描述——"点了没反应"、"这个数据不对"、"页面报错了"、"流程走不下去"等。

**输出**：
- 诊断结论（明确告知问题类型）
- 对应处理（告知正确用法 / 修复代码 / 经用户确认后更新设计文档）
- **不独立产出文档**：文档问题直接在 `magic-align-spec/` 下的现有设计文档（2/3/4/5）原文上修改，不新增目录和编号体系

---

## 诊断流程

### 第一步：澄清现象

用户描述可能比较模糊。先通过追问把现象搞清楚：

- **现象**：实际看到了什么？期望看到什么？
- **复现步骤**：怎么做才能看到这个现象？每次都能复现吗？
- **环境**：哪个页面/哪个功能模块？什么角色账号？
- **关键信息**：有没有报错信息？数据源是什么？操作前后数据对比？

> 如果现象明显（用户描述清晰且有截图/报错），可以跳过追问直接进入第二步。

### 第二步：三层诊断

按照以下顺序逐层判断：

```
用户描述现象
    │
    ▼
┌─────────────────────────────────────────────┐
│ 第 1 层：用户使用方式是否正确？              │
│                                              │
│ 检查：对照操作流程文档（3-operation-flow）    │
│ 看用户的操作步骤是否跟文档一致                │
├─────────────────────────────────────────────┤
│ 不一致 → 第 1 种情况：使用方式问题            │
│ 一致   → 进入第 2 层                         │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ 第 2 层：文档是否正确？                      │
│                                              │
│ 检查：对照详细设计（2-detailed-design）、     │
│ 操作流程（3-operation-flow）、数据库结构      │
│ （4-database-schema）、API 设计（5-api-spec） │
│ 看文档描述的功能行为是否自洽                  │
├─────────────────────────────────────────────┤
│ 文档有误 → 第 3 种情况：文档问题              │
│ 文档正确 → 第 2 种情况：Bug                  │
└─────────────────────────────────────────────┘
    │
    ▼
（文档问题不再深入检查"需求对齐"，直接告知用户文档与实现不符）
```

### 第三步：告知诊断结论

**这是本 skill 的关键环节**。诊断完成后，**必须用明确的标题告知用户问题类型**，让用户一眼知道结论。

#### 第 1 种情况：使用方式问题

**结论标题**：

> ## 诊断结论：使用方式问题

告知用户正确的使用方式，引用操作流程文档中对应的步骤。不需要修改任何文档和代码，流程结束。

```
## 诊断结论：使用方式问题

您当前的操作方式与文档不一致，导致功能未按预期运行。

**正确操作方式**：
（引用操作流程文档中的对应步骤，逐条说明）

**参考文档**：M-XX-operation.md → 测试场景 X.X → 步骤 X
```

#### 第 2 种情况：Bug

**结论标题**：

> ## 诊断结论：这是一个 Bug

明确告知用户这是一个 Bug，文档是正确的，代码有问题。**直接修复代码**，不改文档。

```
## 诊断结论：这是一个 Bug

您操作正确，文档描述的功能也正确，但代码实现与文档不符。

**Bug 定位**：
（描述代码中哪里出了问题）

**修复方案**：
（描述要改什么）

**注意**：不改文档，只修复代码。
```

修复完成后，在操作流程文件中将对应 OP 步骤的"代码实现"状态更新为"已实现"（如果之前是"未实现"）。

#### 第 3 种情况：文档问题

**结论标题**：

> ## 诊断结论：文档问题

告知用户当前文档与实际需求/实现不一致。**展示计划（明确哪些现有文档需要修改） → 等待用户确认 → 直接在原文上修正，不新增 CHG 编号，不追加变更记录**。

```
## 诊断结论：文档问题

您操作正确，但文档描述的功能本身与预期不符。

**问题定位**：
（描述文档中哪里写错了或缺失了什么）

**需要修改的现有文档**：
| 文档 | 修改内容 |
|------|---------|
| ② 模块详细设计 | M-XX.md：xxx 描述需要修正 |
| ③ 操作流程 | M-XX-operation.md：场景 X 步骤 Y 需要调整 |
| ... | ... |

**请注意**：我不会新增变更编号，直接在现有文档上修正。
文档更新后，您可以运行 `/magic-6-code-impl` 让 AI 按新文档重新实现代码。

是否确认按以上计划修改文档？
```

## 执行步骤

### 1. 澄清并定位

询问用户关键信息，定位到具体的功能模块（M-XX）。
检查 `magic-align-spec/` 下是否存在相关文档。

### 2. 对照文档诊断

根据诊断流程逐层判断，每一步都必须有文档依据：

- 引用操作流程文档中对应的 OP 步骤编号
- 引用详细设计中对应的 M-XX 功能描述
- 引用数据库结构或 API 设计中的相关描述

### 3. 告知诊断结论

用明确的标题告知用户问题类型，不允许模糊表述。

| 诊断结果 | 告知用户的话 | 后续操作 |
|---------|------------|---------|
| 使用方式问题 | "**诊断结论：使用方式问题**" | 给出正确用法，结束 |
| Bug | "**诊断结论：这是一个 Bug**" | 直接修复代码，不改文档 |
| 文档问题 | "**诊断结论：文档问题**" | 展示变更计划 → 等用户确认 → 只改文档 |

### 4. 执行操作

根据诊断结果执行对应处理：

- **第 1 种**：告知正确使用方式，结束
- **第 2 种**：直接修复代码（不改文档）→ 验证修复结果
- **第 3 种**：
  1. 展示计划（要改哪些现有文档、改什么内容）
  2. **等待用户明确确认**（"确认，按这个改" / "这里需要调整" / "先不改"）
  3. 用户确认后：**直接在现有文档原文上修正，不新增 CHG 编号，不追加变更记录**
  4. 告知用户后续可通过 `/magic-6-code-impl` 实现代码

## 编写原则

- **先告知再行动**：诊断完成后，必须先用明确的标题告知用户"这是什么问题"，再执行对应操作。不允许跳过告知环节直接动手
- **文档问题必须确认**：涉及文档修改时，必须先展示计划，等用户明确确认后才能动手。用户没点头，就不改
- **文档不改现有编号体系**：8-phenomenon 修改现有设计文档时，直接在原文上修正，不新增 CHG-XXX 变更编号，不追加变更记录。变更编号和变更记录是 `magic-7-req-change` 的职责
- **文档问题不改代码**：文档问题的处理边界是"只改文档，不改代码"。代码由用户自行通过 `/magic-6-code-impl` 实现
- **Bug 不改文档**：Bug 的修复边界是"只改代码，不改文档"。文档是正确的，不需要动
- **文档优先**：每一步判断都必须有文档依据，不能凭经验猜测。没有文档对照的结论不成立
- **引用上游**：涉及功能模块时使用 M-XX 编号，与现有文档体系保持一致
- **一次只处理一个问题**：如果用户描述了多个独立现象，逐个处理
- **分层判断**：严格按照 3 层顺序走，不跳过第 1 层直接去改代码
