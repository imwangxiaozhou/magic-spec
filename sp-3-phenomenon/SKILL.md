用户描述界面上某个**不符合预期的现象**（如点击无反应、数据显示不对、流程走不通等），AI 按三层诊断链路判断问题归属，并执行对应处理：**要么告知正确用法，要么修 Bug，要么改文档再改代码**。

---

**输入**：用户描述的现象。用户可能以任意形式描述——"点了没反应"、"这个数据不对"、"页面报错了"、"流程走不下去"等。

**注意**：本 skill 需**读取相关文档**（详细设计、操作流程等）才能完成诊断。与 sp-1（独立讨论）不同，本 skill 依赖上游文档进行比对。

**输出**：
- 诊断结果 + 执行操作
- 如果涉及文档变更或代码修复，记录写入项目目录的 `magic-align-spec/sp-3-phenomenon/` 目录下：

```
magic-align-spec/sp-3-phenomenon/
├── overview.md                  # 处理记录索引
└── <日期>-<主题>.md             # 单次现象处理记录
```

## 诊断流程

### 第一步：澄清现象

用户描述可能比较模糊。先通过追问把现象搞清楚：

- **现象**：实际看到了什么？期望看到什么？
- **复现步骤**：怎么做才能看到这个现象？每次都能复现吗？
- **环境**：哪个页面/哪个功能模块？什么角色账号？
- **关键信息**：有没有报错信息？数据源是什么？操作前后数据对比？

> 如果现象明显（用户描述清晰且有截图/报错），可以跳过追问直接进入第二步。

### 第二步：三层诊断

按照以下顺序逐层判断：

```
用户描述现象
    │
    ▼
┌─────────────────────────────────────────────┐
│ 第 1 层：用户使用方式是否正确？              │
│                                              │
│ 检查：对照操作流程文档（3-operation-flow）    │
│ 看用户的操作步骤是否跟文档一致                │
├─────────────────────────────────────────────┤
│ 不一致 → 告知用户正确使用方式（第 1 种情况）  │
│ 一致   → 进入第 2 层                         │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ 第 2 层：文档是否正确？                      │
│                                              │
│ 检查：对照详细设计（2-detailed-design）、     │
│ 操作流程（3-operation-flow）、数据库结构      │
│ （4-database-schema）、API 设计（5-api-spec） │
│ 看文档描述的功能行为是否自洽                  │
├─────────────────────────────────────────────┤
│ 文档有误 → 进入第 3 层（改文档）             │
│ 文档正确 → 告知用户是 Bug，直接修复代码      │
│            （第 2 种情况：不改文档只修代码）  │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ 第 3 层：文档与用户需求对不齐？              │
│                                              │
│ 检查：文档描述的功能 ≠ 用户真正需要的功能     │
│ 文档本身自洽但和需求文档/用户预期有偏差       │
├─────────────────────────────────────────────┤
│ 对齐不上 → 先更新文档，再实现代码            │
│            （第 3 种情况：改文档 + 编码）     │
└─────────────────────────────────────────────┘
```

#### 第 1 种情况：用户使用方式有问题

现象：用户操作步骤与操作流程文档不一致，或对某个功能的理解有偏差。

处理：
- 告知用户正确的使用方式，引用操作流程文档中对应的步骤
- 不需要修改任何文档和代码

#### 第 2 种情况：文档正确，是 Bug

现象：用户操作正确，文档描述的功能行为是正确的，但实际代码表现与文档不符。

处理：
- 明确告知用户"这是一个 Bug"
- **不改文档**，直接修复代码
- 代码修复完成后，验证修复结果与文档一致
- 在操作流程文件中将对应 OP 步骤的"代码实现"状态更新为"已实现"（如果之前是"未实现"）

#### 第 3 种情况：文档与实际需求对不齐

现象：用户操作正确，文档描述也自洽，但文档描述的功能本身就不是用户想要的。

处理：
- 先确认用户真正的需求是什么（可借助 sp-1-mvplogic 的讨论方式）
- **从上游文档开始更新**：从受影响的最顶层文档开始，逐级向下更新
  - 可能是 detailed-design（功能描述不对）
  - 可能是 operation-flow（操作步骤需要调整）
  - 可能是 database-schema（表结构不对）
  - 可能是 api-spec（接口不对）
- 文档更新完成后，再实现代码

## 执行步骤

### 1. 澄清并定位

询问用户关键信息，定位到具体的功能模块（M-XX）。
检查 `magic-align-spec/` 下是否存在相关文档。

### 2. 对照文档诊断

根据诊断流程逐层判断，每一步都必须有文档依据：

- 引用操作流程文档中对应的 OP 步骤编号
- 引用详细设计中对应的 M-XX 功能描述
- 引用数据库结构或 API 设计中的相关描述

### 3. 执行操作

根据诊断结果执行对应处理：

- **第 1 种**：输出诊断结论 + 正确使用方式
- **第 2 种**：输出诊断结论 → 修复代码（不改文档）→ 验证
- **第 3 种**：输出诊断结论 → 更新受影响的所有文档 → 实现代码 → 验证

### 4. 记录

每次处理写入一个记录文件到 `magic-align-spec/sp-3-phenomenon/`：

- 现象描述
- 诊断链路（逐层结论）
- 处理方式
- 修改的文件列表

## 编写原则

- **文档优先**：每一步判断都必须有文档依据，不能凭经验猜测。没有文档对照的结论不成立
- **不改不相关的东西**：第 2 种情况只改代码不改文档，第 3 种情况先改文档再改代码。不越界修改
- **引用上游**：涉及功能模块时使用 M-XX 编号，与现有文档体系保持一致
- **一次只处理一个问题**：如果用户描述了多个独立现象，逐个处理
- **分层判断**：严格按照 3 层顺序走，不跳过第 1 层直接去改代码
