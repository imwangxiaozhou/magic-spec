记录需求变更，评估变更对已有设计文档（1~5）的影响范围，逐文档更新并追加变更记录。本 Skill 只更新文档，不实现代码。代码实现由 `magic-6-code-impl` 负责。

---

**前置条件**：
- `magic-align-spec/1-tech-implementation-plan/overview.md` 必须已生成
- 文档 2~5 按需存在（存在则评估影响，不存在则跳过）

**输入**：用户描述的需求变更内容（文字描述、PRD 修订片段、或变更清单）。

**输出**：更新受影响的设计文档，在每个受影响文档中追加变更记录。

---

## 执行步骤

### 1. 理解变更内容

向用户确认变更内容，确保理解准确：

- 读取用户提供的变更描述
- 如果描述不够清晰，使用 **AskUserQuestion** 追问：变更涉及哪些模块、具体改了什么、为什么改
- 确认变更范围：是新增功能、修改已有功能、还是删除功能

### 1.1 分配变更编号

为本变更分配唯一编号，格式为 `CHG-XXX`（如 CHG-001、CHG-002）：

- 检查文档 1~5 中已有的变更记录，取最大编号 +1
- 如果尚无任何变更记录，从 CHG-001 开始
- 该编号在本次变更涉及的所有文档（1~5）中保持一致
- 后续 `magic-6-code-impl` 实现代码时沿用此编号

### 2. 需求深度讨论

在评估文档影响之前，与用户就需求本身进行充分讨论。讨论结果不全部写入设计文档，但讨论过程帮助发现潜在问题，避免后续返工。

围绕以下五个维度展开讨论，使用 **AskUserQuestion** 逐维度确认用户意图：

#### 2.1 需求背景与动机

- 为什么要做这个变更？解决什么问题？
- 如果不做这个变更，用户当前的替代方案是什么？
- 这个变更的优先级如何？有没有时间约束？

#### 2.2 前端界面设计（如涉及前端）

如果变更涉及用户可见的界面，必须讨论：

- 页面布局：新增页面还是在现有页面上修改？放在哪个菜单下？
- 交互流程：用户的操作路径是怎样的？（如：点击按钮 → 弹出表单 → 提交 → 列表刷新）
- 关键交互细节：表单字段、按钮位置、弹窗/抽屉、确认提示、错误提示
- 是否需要新增路由或菜单入口？

讨论结论作为后续更新文档 3（操作流程）的前端操作步骤依据。

#### 2.3 对现有功能的影响面

- 本次变更会影响哪些已有功能？（直接影响的模块、间接影响的关联模块）
- 是否有其他功能依赖被修改的 API 或数据表？
- 变更后，已有的数据是否需要迁移或清洗？
- 是否需要同步修改其他模块的代码？（如共用组件、工具函数）

#### 2.4 潜在风险与不利方面

- 是否存在性能风险？（如新增查询导致慢 SQL、大数据量下的前端渲染）
- 是否存在数据一致性风险？（如并发操作、事务边界）
- 是否存在兼容性风险？（如老版本客户端、第三方集成）
- 是否有安全方面的考虑？（如权限校验、数据越权）
- 变更失败后的回滚方案是什么？

对于识别出的风险，与用户确认是否需要在本次变更中一并处理，还是记录为已知风险后续跟进。

#### 2.5 替代方案与扩展可能

- 有没有比当前方案更简单的实现方式？（如复用现有组件、用配置代替开发）
- 这个变更未来是否可能进一步扩展？（如当前只支持单个，未来可能批量操作）
- 如果有扩展可能，是否需要预留扩展点？（如字段设计时预留类型字段、API 设计时考虑分页）
- 有没有行业通用的最佳实践可以参考？

用户确认不需要预留扩展的，不在本次设计中过度设计。

> **讨论原则**：不追求每个维度都有结论，但每个维度都必须过一遍。用户明确表示"不需要讨论"的维度可以跳过。讨论结论中影响设计的部分（如前端交互流程、影响面、风险应对）写入后续文档更新的内容中。

### 3. 检查已有文档

依次检查文档 1~5 是否存在：

| 文档编号 | 文档路径 | 说明 |
|---------|---------|------|
| 1 | magic-align-spec/1-tech-implementation-plan/ | 技术方案设计（overview.md + T-XX-*.md） |
| 2 | magic-align-spec/2-detailed-design/ | 模块详细设计（overview.md + M-XX-*.md） |
| 3 | magic-align-spec/3-operation-flow/ | 测试操作流程（overview.md + M-XX-*-operation.md） |
| 4 | magic-align-spec/4-database-schema/ | 数据库表结构（overview.md + M-XX-*.md） |
| 5 | magic-align-spec/5-api-spec/ | API 接口设计（overview.md + M-XX-*-api.md） |

- 存在的文档：进入影响评估
- 不存在的文档：跳过，不评估

### 4. 评估影响范围

逐个分析变更对每份已有文档的影响：

**文档 1（技术方案）**：
- **原则：文档 1 中的 T-XX 是一个可独立开发的较大功能单元，评估时尽量不修改文档 1**
- 仅在以下情况才修改文档 1：
  - 需要新增/删除技术方案（T-XX）
  - 方案间交互关系（I-XX）有本质性变更
  - 技术栈选型有根本性调整
- 不应修改的情况：
  - 功能模块（M-XX）的增删改（属于文档 2 的范围）
  - 表结构或 API 的微调（属于文档 4、5 的范围）
  - 操作步骤的调整（属于文档 3 的范围）

**文档 2（详细设计）**：
- 是否需要新增/修改/删除模块（M-XX）？
- 数据表结构是否需要调整（加字段、改约束）？
- 服务模块的功能点划分是否变化？
- 模块依赖关系是否变化？
- 工时评估是否需要修正？

**文档 3（操作流程）**：
- 是否需要新增/修改/删除测试场景？
- 操作步骤或后端影响描述是否需要更新？
- 已有的"已实现"标记是否需要回退为"未实现"？

**文档 4（数据库结构）**：
- 是否需要新增/修改/删除数据表？
- 字段类型、约束是否需要调整？
- 索引是否需要变更？
- 外键关系是否变化？
- DDL 是否需要更新？

**文档 5（API 接口）**：
- 是否需要新增/修改/删除 API 接口？
- 请求参数或响应字段是否变更？
- 错误码是否需要新增或调整？

使用 **AskUserQuestion** 向用户确认影响评估结果：列出受影响的文档编号和影响摘要，让用户确认或补充。

### 5. 更新文档（按 1 → 2 → 3 → 4 → 5 顺序）

对每个受影响的文档，按编号顺序依次更新：

**5.1 更新文档内容**

根据变更内容，直接修改文档中对应的章节：
- 新增内容：插入到合适的位置，遵循文档原有的格式和编号规则
- 修改内容：更新对应段落，保持编号不变
- 删除内容：标记为已删除或直接移除（根据用户偏好）

**5.2 追加变更记录**

在受影响文档顶部的文档信息表格后，追加变更记录（按时间倒序排列，最新在最前）：

```
> **变更记录**：
> - CHG-XXX | yyyy-mm-dd | {变更摘要} | 影响：{受影响的文档编号，用/分隔} | 代码：未实现
```

- **CHG-XXX**：本次变更的唯一编号
- **变更摘要**：一句话描述改了什么
- **影响**：列出本次变更涉及的所有文档编号，如 `1/2/4`
- **代码**：固定标记为 `未实现`（本 Skill 不实现代码）

### 6. 输出变更总结

向用户展示变更总结：

```
## 需求变更总结

**变更编号**：CHG-XXX

**变更描述**：{用户提供的变更描述}

**受影响的文档**：
| 文档编号 | 文档名称 | 变更内容摘要 | 状态 |
|---------|---------|------------|------|
| 1 | 技术方案设计 | {具体改了什么} | 已更新 |
| 2 | 模块详细设计 | {具体改了什么} | 已更新 |
| 4 | 数据库表结构 | 未受影响 | — |

**后续行动**：
- 使用 `magic-6-code-impl` 实现受影响的代码
- 受影响的操作步骤已标记为"未实现"，需重新实现
```

## 编写原则

- **只改文档不写代码**：本 Skill 的职责边界是文档更新，不涉及任何代码实现
- **先讨论再评估**：确定变更编号后，先与用户深度讨论需求背景、前端设计、影响面、风险和替代方案，再进入文档影响评估
- **前端设计必讨论**：涉及用户可见界面的变更，必须讨论前端布局和交互流程，避免后续实现时前端被遗漏
- **按顺序更新**：受影响文档按 1 → 2 → 3 → 4 → 5 的顺序依次更新，确保上游文档先改
- **变更记录必追加**：每个受影响的文档都必须追加变更记录，方便后续追溯
- **代码标记为未实现**：变更记录中的"代码"字段固定为"未实现"，提醒开发者后续需要实现
- **编号保持一致**：新增的模块编号（M-XX）、技术方案编号（T-XX）、API 编号（API-XX）与现有文档保持连续。变更编号（CHG-XXX）在所有受影响文档中保持一致
- **影响评估要确认**：评估完影响范围后必须让用户确认，避免遗漏或误判
- **文档 1 尽量不动**：文档 1 的 T-XX 是较大功能单元，评估时尽量不修改，仅在方案级变更时才修改

## 典型使用场景

### 场景一：PRD 新增功能

用户在开发过程中收到新的 PRD 补充（如渠道活码详细设计补充）：
1. 描述变更：渠道活码管理的详细设计已补充
2. 评估影响：文档 2（新增模块功能点）、文档 3（新增测试场景）、文档 4（可能新增字段）、文档 5（新增 API）
3. 更新文档 → 追加变更记录

### 场景二：技术选型调整

用户在实现过程中发现需要调整技术方案：
1. 描述变更：数据库从 PostgreSQL 改为 MySQL
2. 评估影响：文档 1（技术栈变更）、文档 4（DDL 语法差异）
3. 更新文档 → 追加变更记录

### 场景三：设计缺陷修正

用户在实现过程中发现设计不合理：
1. 描述变更：agents 表需要新增 priority 字段支持优先级排序
2. 评估影响：文档 2（模块功能点）、文档 3（操作步骤）、文档 4（表结构）、文档 5（API 参数）
3. 更新文档 → 追加变更记录
