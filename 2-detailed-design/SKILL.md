基于第 1 份文档（技术方案实现）衍生，以数据库表为一级模块进行详细设计。同一张表上的操作（增删改查、状态变更等）归到同一个一级模块下，同时包含该模块对应的前端页面/组件。按优先级梯度展开，明确依赖关系、需求原文、预估工时（人和 AI 联合开发时间）。不涉及数据库表字段/类型/约束设计（属于技能 4）和 API 路径/参数/响应设计（属于技能 5）。

---

**前置条件**：`magic-align-spec/1-tech-implementation-plan/overview.md` 必须已生成。

**输入**（二选一）：
- **文档模式**：第 1 份技术方案设计文档 + 需求文档/PRD
- **代码分析模式**：分析现有项目代码，从代码中提取已有业务模块和前端页面结构。需要用户确认后才执行代码分析

**输出**：详细设计文档（Markdown 格式），按模块拆分为多个文件，写入当前项目目录的 `magic-align-spec/2-detailed-design/` 目录下：

```
magic-align-spec/2-detailed-design/
├── overview.md              # 总览：文档信息、总体数据流、模块总览表、工时汇总、依赖关系与开发顺序、风险与待确认项
├── M-01-<模块英文名>.md      # 单个模块的详细设计（基本信息、需求原文、功能拆解）
├── M-02-<模块英文名>.md
└── ...
```

- `overview.md` 包含全局信息（数据流、模块总览、工时汇总、开发顺序、风险）
- 每个 `M-XX-<模块英文名>.md` 包含该模块的详细设计
- 新增模块时追加新的 M-XX 文件，修改模块时只更新对应文件

## 执行步骤

### 1. 前置检查

检查 `magic-align-spec/1-tech-implementation-plan/overview.md` 是否存在：

- **存在**：读取该目录下的 overview.md 和各 T-XX-*.md 文件，提取技术方案（T-XX）列表作为输入
- **不存在**：告知用户「尚未生成技术方案设计文档，请先使用 magic-tech-design 生成后再执行本步骤」，终止流程

### 2. 技术方案确认状态检查

读取 `magic-align-spec/1-tech-implementation-plan/` 目录下 overview.md 中每个技术方案（T-XX）的"确认状态"字段：

- **全部已确认**：正常继续
- **存在待确认或存疑的方案**：使用 **AskUserQuestion** 逐项向用户确认：
  - 待确认的方案：询问"T-XX {方案名称} 的技术选型 {当前选型} 是否确认？如有调整请说明"
  - 存疑的方案：询问"T-XX {方案名称} 当前存疑，原因：{存疑原因}。请确认最终方案或提供替代方案"
  - 根据用户回复，**更新 `magic-align-spec/1-tech-implementation-plan/` 目录下对应方案文件**中对应方案的确认状态（待确认→已确认/存疑，存疑→已确认/更新方案内容）
- 确认完成后继续执行

### 3. 确认输入

向用户确认输入方式：

- **文档模式**：如果用户提供了需求文档位置，直接读取。否则使用 **AskUserQuestion** 询问需求文档/PRD 的位置
- **代码分析模式**：如果用户选择分析代码，扫描项目中的 ORM 模型/SQL 文件提取表名列表（不提取字段细节），再从目录结构中识别已有的前端页面。分析前向用户说明分析范围和将要检查的文件

### 4. 识别数据表和服务

从需求文档和技术方案中识别：

- **数据表级模块**：每个数据库表作为一个一级模块。从需求中提取该表需要支持的 CRUD 操作、状态变更、级联操作等作为后端二级功能点，同时识别该模块对应的前端页面/组件作为前端二级功能点
- **服务级模块**：不直接对应数据库表的服务功能（如路由调度、消息处理、定时任务、数据同步等），每个服务作为一个一级模块

同一个模块编号（M-XX）下，后端功能点用 M-XX-01~09，前端功能点用 M-XX-10+。

### 5. 按梯度编写详细设计

按优先级从高到低（P0 → P1 → P2）逐模块展开。每个模块独立成章。

### 6. 输出

将文档按模块拆分为多个文件，写入 `magic-align-spec/2-detailed-design/` 目录：

1. 先写 `overview.md`，包含文档信息、总体数据流、模块总览表、工时汇总、依赖关系与开发顺序、风险与待确认项
2. 再逐模块写 `M-XX-<模块英文名>.md`，每个文件包含该模块的详细设计
3. 汇总总工时和关键路径

## 编写原则

- **表级优先**：以数据库表为一级模块划分单位，同一张表的操作归到一起。先梳理所有数据表，再补充服务级模块
- **表名是标识不是设计**：基本信息中标注"对应数据表"用于标识模块管理哪张表，但不展开表的字段、类型、约束、索引（属于技能 4）
- **不越界设计**：不输出 API 路径/方法/参数/响应（属于技能 5），不输出数据库表字段/类型/约束/索引（属于技能 4）。功能拆解中的"业务描述"只描述做什么，不描述怎么做
- **前后端都覆盖**：每个模块必须考虑前端是否需要对应页面/组件。涉及用户交互的功能必须有前端功能点（M-XX-10+），不允许只有后端而没有前端
- **两级编号**：一级模块用 `M-XX`，后端功能点用 `M-XX-01~09`，前端功能点用 `M-XX-10+`，结构清晰可追溯
- **梯度优先**：严格按 P0 → P1 → P2 顺序展开，P0 模块要最详细
- **可追溯**：每个模块必须引用需求文档原文，标注来源章节
- **依赖明确**：数据表间通过 FK 确定依赖关系，服务模块标注依赖的数据表和服务
- **工时务实**：预估工时为人和 AI 联合开发所用时间。AI 负责生成代码框架和模板，人负责架构决策、代码审查、联调自测。纯 CRUD 类功能工时大幅缩短，复杂逻辑类功能仍需较多人工投入
- **引用上游**：技术方案编号（T-XX）必须与第 1 份文档保持一致
- **按模块拆分文件**：每个 M-XX 一个独立文件，overview.md 放全局信息
