根据操作流程文档中的操作步骤（OP-XX），逐功能实现前后端代码。**前端采用设计驱动**：实现前端代码前，先为该功能的 UI 制定独特的设计方案（色彩、字体、布局、交互），评审确认后再编写测试和实现代码。实现前先分析代码变更是否影响现有设计文档，如有影响则先更新文档再编码。

---

**前置条件**：

- `magic-align-spec/1-tech-implementation-plan/overview.md` 必须已生成
- `magic-align-spec/2-detailed-design/overview.md` 必须已生成
- `magic-align-spec/3-operation-flow/overview.md` 及对应模块的操作流程文件必须已生成
- `magic-align-spec/4-database-schema/overview.md` 必须已生成
- `magic-align-spec/5-api-spec/overview.md` 必须已生成

**输入**：用户可指定要实现的 OP 编号，不指定则自动选取第一个"未实现"的操作步骤。

**输出**：实现对应功能的前后端代码，更新受影响的文档。

---

## 执行步骤

### 1. 确定实现目标

读取 `magic-align-spec/3-operation-flow/` 目录下的操作流程文件（`overview.md` + 各 `M-XX-*-operation.md`），查找"代码实现"列：

- **用户指定了 OP 编号**：定位到对应步骤，作为实现目标
- **用户未指定**：从上到下遍历所有操作步骤表格，找到第一个标记为"未实现"的步骤，作为实现目标
- **全部已实现**：告知用户所有功能均已实现，无需继续

确定目标后，向用户确认：要实现的步骤编号、步骤描述摘要。

### 1.1 判断实现类型与变更编号

确认实现目标后，判断本次实现属于哪种类型：

**首次实现**（项目中尚无已实现的代码，非修改或新增需求）：
- 生成完整的数据库迁移脚本（DDL），包含所有表结构的建表语句
- 无需生成变更编号，变更记录中不追加编号
- 文档 1~5 中已有的变更记录（由 `magic-7-req-change` 产生），其 `代码` 字段保持 `未实现`，待对应 OP 实现后更新

**后续变更**（已有代码基础上修改或新增需求）：
- 生成本次变更的唯一编号，格式为 `CHG-XXX`（如 CHG-001、CHG-002），编号按已有变更记录中的最大编号递增
- 该编号在本次变更涉及的所有文档（1~5）中保持一致
- 如果涉及数据库操作，生成增量迁移脚本（仅包含本次修改的表/字段的 ALTER/CREATE 语句，文件名包含变更编号如 `migration_CHG-001.sql`）

### 1.2 分析模块关联和文档影响

从目标步骤的"后端影响"列中提取涉及的：

- API 路径和方法
- 数据表（INSERT/UPDATE/DELETE/SELECT 涉及的表名）
- 模块编号（M-XX）

然后检查现有代码和文档的一致性，判断是否需要更新以下文档：

**文档 1（技术方案）**：

- **原则：文档 1 中的 T-XX 是一个可独立开发的较大功能单元，评估时尽量不修改文档 1**
- 仅在以下情况才修改文档 1：
  - 需要新增/删除技术方案（T-XX）
  - 方案间交互关系（I-XX）有本质性变更
  - 技术栈选型有根本性调整
- 不应修改的情况：
  - 功能模块（M-XX）的增删改（属于文档 2 的范围）
  - 表结构或 API 的微调（属于文档 4、5 的范围）
  - 操作步骤的调整（属于文档 3 的范围）

**文档 2（详细设计）**：

- 实现过程中发现数据表结构需要调整（加字段、改约束）
- 发现服务模块的功能点划分不准确
- 工时评估需要修正

**文档 3（操作流程）**：

- 操作步骤或后端影响描述与实际实现有出入

**文档 4（数据库结构）**：

- 表结构有变更（新增字段、修改类型、调整约束）
- 索引调整
- 表间关系变更

**文档 5（API 接口）**：

- API 路径或方法变更
- 请求参数或响应字段变更
- 错误码新增或调整

**判断原则**：如果代码实现完全按照文档设计进行，无需修改文档。只有在实现中发现设计需要调整时才修改文档。

### 1.3 回顾变更讨论结论（如有关联 CHG-XXX）

如果本次目标步骤关联了一个变更编号（由 `magic-7-req-change` 产生的 CHG-XXX），需要回顾该变更在文档中的讨论结论：

- 检查文档 3 对应模块操作流程文件中的变更记录，找到对应的 CHG-XXX 记录
- 检查文档 1~5 中该 CHG-XXX 的变更记录，提取讨论中确定的：
  - **前端设计决定**：页面布局、交互流程、路由入口（确保实现时不遗漏前端）
  - **影响面**：哪些已有功能会受影响，是否需要同步修改其他模块
  - **风险点**：讨论中识别的性能/数据/安全风险，实现时是否需要特殊处理
  - **扩展预留**：讨论中是否决定预留扩展点（如字段类型、API 分页）

如果变更记录中缺少这些信息（说明 `magic-7-req-change` 讨论不充分），应暂停实现，先返回 `magic-7-req-change` 补充讨论后再继续。

### 3. 更新文档（如有需要）

如果步骤 1.2 判断需要修改文档，按文档编号顺序（1 → 2 → 3 → 4 → 5）依次更新：

- 更新对应文档内容
- 在文档顶部的文档信息表格后，追加变更记录（按时间倒序排列，最新在最前）：

**首次实现**（无变更编号）：
```
> **变更记录**：
> - yyyy-mm-dd | {变更摘要} | 影响：{受影响的文档编号，用/分隔} | 代码：{已实现/未实现}
```

**后续变更**（带变更编号 CHG-XXX）：
```
> **变更记录**：
> - CHG-XXX | yyyy-mm-dd | {变更摘要} | 影响：{受影响的文档编号，用/分隔} | 代码：{已实现/未实现}
```

- 如果仅实现代码而未修改文档设计，不追加变更记录
- **影响**字段：列出本次变更涉及的文档编号，如 `1/2/4` 表示影响了技术方案、详细设计和数据库结构
- **代码**字段：`已实现` 表示对应功能的代码已编写完成，`未实现` 表示仅更新了文档设计但代码尚未实现

> **职责边界**：本步骤仅处理实现过程中发现的**小幅设计调整**（如字段类型微调、补充遗漏字段等）。
> 如果是**需求级别的变更**（新增功能、删除功能、技术选型调整、PRD 修订等），应停止实现，先使用 `magic-7-req-change` 完成文档变更后再继续。

### 4. 编写测试（实现后验证）

实现代码**之后**编写测试，验证代码的正确性。测试用例覆盖本次功能的所有核心逻辑，前后端都必须有测试。

#### 4.1 后端测试

后端代码实现后（步骤 5），根据实际代码编写后端测试：

- **API 接口测试**：覆盖正常请求和异常请求（参数校验、权限校验、边界值），验证响应状态码和响应体结构
- **Service 层测试**：覆盖核心业务逻辑（正常流程、异常流程、边界条件），mock 外部依赖（数据库、第三方服务）
- **数据层测试**（如有）：验证 DAO 操作的 SQL 正确性（可选使用内存数据库或测试数据库）

后端测试文件放在项目测试目录中，与被测代码的目录结构对应。

#### 4.2 前端测试

前端代码实现后（步骤 6.4），根据实际页面/组件编写前端测试：

- **组件渲染测试**：验证页面/组件能正常渲染，关键 DOM 元素存在（表单字段、按钮、列表列头等）
- **交互行为测试**：验证用户操作触发正确的事件处理（按钮点击、表单提交、弹窗打开/关闭）
- **API 调用测试**：验证前端调用后端 API 的请求参数正确，并正确处理响应（mock API 返回）

前端测试文件放在项目前端测试目录中，与页面/组件文件对应。

#### 4.3 测试通过标准

- 实现代码后编写测试，所有测试用例必须**全部通过**
- 如有测试未通过，先修复代码再重新运行，直到全部通过为止
- 如有需要可重构代码，但重构后测试仍须全部通过

> **强制要求**：前后端测试均不可省略。测试不通过，不得标记功能为已完成。

### 5. 实现后端代码

按目标步骤的"后端影响"描述实现后端：

- 实现 API 接口（路由、控制器、校验逻辑）
- 实现数据变更（Service 层、DAO 层）
- 实现调用逻辑（事务、级联操作、外部调用）

后端实现遵循文档 5 中的接口设计（路径、参数、响应格式）。

**数据迁移脚本**：

- **首次实现**：生成完整的数据库迁移脚本（DDL），包含所有表结构的建表语句、索引、初始数据等。文件放在 `migrations/` 目录下，如 `migrations/001_init.sql`
- **后续变更**：如果涉及数据库操作，生成增量迁移脚本，仅包含本次修改部分的 SQL（ALTER TABLE、CREATE TABLE 新表、CREATE INDEX 等）。文件名包含变更编号，如 `migrations/migration_CHG-001.sql`

### 6. 前端设计驱动实现

前端代码实现分为三个阶段：**设计方案 → 实现代码 → 编写测试**。先设计，再编码，后测试。

#### 6.1 制定前端设计计划

在写任何前端代码之前，先为当前功能/页面制定一个紧凑的设计方案。把自己当作一个独立工作室的设计负责人——每个项目都应该有独特的视觉识别，而不是套模板。

**设计计划包含四个要素**：

**① 色彩（Color Palette）**：
定义 4-6 个命名色值（hex），包括：
- 主色（Primary）：品牌/核心交互色
- 辅色（Secondary）：辅助功能色
- 中性色（Neutral）：背景、边框、文字色阶
- 语义色（Semantic）：成功、警告、错误（如果功能需要）
- 强调色（Accent）：用于引导注意力的点缀色，谨慎使用

> **不要**落入 AI 设计的三个默认陷阱：(1) 暖白背景 + 高对比衬线 + 陶土红；(2) 近黑背景 + 荧光绿/朱红；(3) 报章风格 + 极细分割线 + 零圆角。除非当前功能确实适合。

**② 字体（Typography）**：
选择 2-3 个有目的的字体角色：
- 展示字体（Display）：用于标题/品牌元素，有性格，克制使用
- 正文字体（Body）：用于主要内容，清晰可读
- 辅助字体（Utility，可选）：用于标注/数据/说明文字

定义字号层级（如 h1/h2/h3/body/caption），以及对应的字重和行高。让字体本身成为设计记忆点，而不是内容的被动载体。

**③ 布局（Layout）**：
用一句话描述 + ASCII 线框图表达布局概念。关注：
- 页面结构：导航 → 内容区 → 操作区 的层次关系
- 信息层级：哪些信息优先展示，哪些折叠/次要
- 响应式策略：桌面端 → 平板的 breakpoint

```
+------------------------------------------+
|  Header / 导航                            |
+------------------------------------------+
|  标题区域（主色点缀）                      |
|  ┌──────────────┐  ┌────────────────────┐ |
|  |  侧边筛选      |  |  主体内容列表       | |
|  |  □ 筛选A      |  |  ┌──┐ ┌──┐ ┌──┐   | |
|  |  □ 筛选B      |  |  │  │ │  │ │  │   | |
|  |              |  |  └──┘ └──┘ └──┘   | |
|  └──────────────┘  └────────────────────┘ |
+------------------------------------------+
```

**④ 签名元素（Signature）**：
定义这个页面/功能最独特的单个记忆点——用户在 5 秒后还能记住的东西。它可以是一个大胆的颜色块、一个特殊的交互手势、一个非标准的布局切分。**只有一个**，其他地方保持克制。

#### 6.2 评审设计计划

设计计划制定后，进行自我评审：

- 这个设计计划是否和其他任何页面看起来一样？如果是——修改它
- 色彩是否是用户当前项目的延续（读取项目中已有的 CSS 变量或设计 token）？如果是——继承统一 token，在当前功能中做合理衍生
- 签名元素是否真的独特？有没有比当前选择更大胆的替代方案？
- 如果用户有前端设计风格的偏好（之前的设计中体现过），是否遵循了？

确认设计计划有独特性后，再进入编码阶段。所有颜色和字体决策都从该计划中派生。

#### 6.3 实现前端代码

严格按照 6.1 的设计计划实现前端代码：

- 建立 CSS token 系统（从设计计划中提取颜色、字体、间距变量）
- 实现布局结构（导航、内容区、操作区）
- 实现功能组件（表单、列表、弹窗、状态切换）
- 实现签名元素（确保它是这个页面最独特的记忆点）
- 响应式适配（桌面端为主，平板端不低于基础可用）

**CSS 注意事项**：
- 使用 CSS 自定义属性（变量）统一管理 token
- 避免选择器特异性冲突（如 `.section` vs `.cta` 互相覆盖）
- 间距/内外边距保持 token 化的一致性
- 响应式断点统一管理

**交互注意事项**：
- 动效：有目的地使用（加载过渡、悬停反馈、状态切换），但不多余
- 空状态：没有数据时，给出引导性提示而非空白页
- 加载状态：关键操作（提交、查询）必须有 loading 反馈
- 错误状态：错误信息说明发生了什么以及如何解决
- 键盘焦点可见、减动效（`prefers-reduced-motion`）被尊重

#### 6.4 编写前端测试

前端代码实现后，根据实际页面/组件编写前端测试：

- **组件渲染测试**：验证页面/组件能正确渲染，关键 DOM 元素存在（表单字段、按钮、列表列头等）
- **交互行为测试**：验证用户操作触发正确的事件处理（按钮点击、表单提交、弹窗开闭）  
- **API 调用测试**：验证前端调用后端 API 的请求参数正确，并正确处理响应（mock API 返回）

#### 6.5 验证测试通过

运行前端测试，确认所有用例通过。结合步骤 7 一起验证前后端联调。

实现目标：使 6.4 中编写的前端测试全部通过，且最终 UI 与 6.1 的设计计划一致。

### 7. 验证测试通过

代码实现完成后，运行全部测试（前后端），确认：

- 步骤 4.1 编写的后端测试全部通过
- 步骤 6.4 编写的前端测试全部通过
- 已有的旧测试没有因本次变更而破坏（回归测试）

如有测试未通过，修复代码后重新运行，直到全部通过为止。

### 8. 标记实现状态

#### 8.1 更新操作流程状态

更新 `magic-align-spec/3-operation-flow/` 目录下对应模块操作流程文件中步骤的"代码实现"列：

- `未实现` → `已实现`

如果实现涉及多个 OP 步骤（一个功能可能关联多个步骤），将所有受影响的步骤标记为已实现。

#### 8.2 同步变更记录状态

代码实现完成后，优先检查对应的 OP 步骤是否已完成（"代码实现"列变为"已实现"）：

- 如果 OP 已完成，从文档 3 的变更记录中查找本次实现对应的变更编号（CHG-XXX）
- 在文档 1~5 中查找该 CHG-XXX 对应的变更记录，将其 `代码` 字段从 `未实现` 更新为 `已实现`
- 如果文档 1~5 中没有找到对应的 CHG-XXX 记录（首次实现），则在受影响的文档变更记录中追加一条标记为 `代码：已实现` 的记录

这样每次修改的状态变更都清晰可追溯：变更编号贯穿所有文档，`代码` 字段明确标识该变更的代码是否已实现。

## 编写原则

- **每次一个功能**：一次只实现一个操作步骤（OP 编号对应的一行），不批量实现
- **文档优先**：先判断文档是否需要更新，再写代码。先改文档，后写代码
- **前端设计驱动**：实现前端代码前，必须制定设计计划（色彩、字体、布局、签名），评审确认后再编码。每个功能页面应有独特的视觉识别，不套模板
- **先编码后测试**：统一先写代码，再编写测试验证正确性。后端代码实现后编写测试，前端设计计划确定并实现后编写测试。确保所有核心交互路径被覆盖
- **变更讨论必回顾**：如果目标步骤关联 CHG-XXX，实现前必须回顾 `magic-7-req-change` 讨论结论（前端设计、影响面、风险点），讨论不充分则暂停实现
- **前后端一起**：一个功能的前端和后端在同一次实现中完成
- **前端不可跳过**：前端设计计划和前端测试都必须完成，不允许以"功能简单"等理由跳过前端环节
- **标记变更**：修改了文档就要标注变更记录，方便后续追溯
- **引用上游**：模块编号（M-XX）、API 编号（API-XX）与各前置文档保持一致
- **变更编号统一**：后续变更必须使用 CHG-XXX 编号，同一变更在所有文档中使用相同编号
- **状态同步**：代码实现完成后，优先检查 OP 完成状态，同步更新文档 1~5 中对应 CHG-XXX 的 `代码` 字段
- **数据库脚本分首次/增量**：首次实现生成完整 DDL，后续变更生成增量迁移脚本（带 CHG 编号）
- **文档 1 尽量不动**：文档 1 的 T-XX 是较大功能单元，评估和实现时尽量不修改，仅在方案级变更时才修改
- **可配置项禁止硬编码**：任何可能变化的参数（超时时间、重试次数、开关阈值、外部 URL、分页大小、文件路径、第三方 Key 等）必须写入配置文件或环境变量，不得硬编码在代码中。代码中只能引用配置，不能直接写死值
- **Docker 文件随代码同步更新**：实现代码时如果新增了依赖、环境变量、端口、挂载路径或服务，必须同步更新 Dockerfile 和 docker-compose.yml。目标：`docker compose up` 一键启动即可用

## 实现约束

每次实现代码时，以下内容统一遵循。

### 日志规范

每个技术方案（T-XX）在实现时，必须包含统一的日志输出：

- **日志框架**：与项目技术栈一致的常用日志库（如 Python 用 logging、Node.js 用 winston、Go 用 slog/zap、Java 用 SLF4J）
- **日志级别**：
  - `DEBUG`：开发调试信息（变量值、中间状态）
  - `INFO`：关键业务节点（请求到达、数据写入、外部调用、任务启动/完成）
  - `WARN`：可恢复的异常（重试、降级、数据不一致）
  - `ERROR`：不可恢复的错误（异常捕获、外部调用失败）
- **日志格式**：每条日志包含时间戳、级别、模块名、请求ID（如有）、消息内容
- **日志输出**：开发环境输出到 stdout，生产环境输出到文件或日志中心
- **关键节点必须打日志**：
  - API 请求入口和出口（路径、方法、耗时、状态码）
  - 数据库写操作（INSERT/UPDATE/DELETE 的表名和影响行数）
  - 外部服务调用（调用方、接口、耗时、结果）
  - 事务提交/回滚
  - 定时任务启动和完成

### 配置文件规范

每个技术方案（T-XX）在实现时，必须包含配置文件：

- **配置文件位置**：方案目录下的 `config/` 或根目录，与环境变量配合使用
- **配置分层**：
  - `default`：默认配置，提交到代码仓库
  - `development`：本地开发环境（可提交）
  - `production`：生产环境（敏感信息用环境变量，不提交）
- **配置项至少包含**：
  - 服务端口和监听地址
  - 数据库连接信息（host、port、database、user、password，密码用环境变量）
  - 外部服务地址和密钥（用环境变量）
  - 日志级别和输出路径
- **环境变量命名**：大写蛇形，前缀统一为项目英文名缩写，如 `APP_DB_HOST`、`APP_REDIS_URL`
- **配置读取优先级**：环境变量 > 配置文件 > 默认值
- **配置项必须有注释**：每个配置项必须附带注释，说明：
  - 该项的作用（一句话）
  - 值的格式/单位（如"毫秒"、"秒"、"bytes"、"http://host:port"）
  - 有效范围（如"1-3600"、"debug/info/warn/error"）
  - 修改后果（如"超过 30 秒可能触发网关超时"）

### Docker 文件同步

代码实现涉及以下情况时，必须同步更新 Docker 相关文件：

- **新增依赖包**：`requirements.txt` / `package.json` / `go.mod` 等依赖清单变更后，需确认 Dockerfile 中的安装步骤是否仍然有效
- **新增环境变量**：`.env` 或 `config.yaml` 新增配置项后，需同步到 `docker-compose.yml` 的 `environment` 段
- **新增端口**：服务监听了新端口，需在 `docker-compose.yml` 的 `ports` 段暴露
- **新增挂载目录**：代码输出到新路径（日志、上传文件等），需在 `docker-compose.yml` 的 `volumes` 段挂载。**日志挂载特别注意**：必须保证三对齐——① 宿主机 `logs/<service-name>/` 目录存在 ② `docker-compose.yml` 中挂载 `./logs/<service-name>:/app/logs` ③ 代码中日志输出路径与容器内挂载路径一致（如 `/app/logs/`）。漏掉任何一环，日志要么写不进去要么丢在容器里
- **新增服务**：新增了一个可独立部署的方案（T-XX），需在 `docker-compose.yml` 中添加对应服务定义

**原则**：本地能跑不代表容器里能跑。每次实现后检查：如果别人拉下代码执行 `docker compose up`，能不能直接跑起来？
