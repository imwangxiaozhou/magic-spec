# 🧙 Magic-Spec — AI 驱动的全流程开发规约引擎

> *"先对齐再动手，每一步都可追溯，每一行代码都有据可查。"*

Magic-Spec 是一套 **AI 辅助的软件开发规约方法论 + 工具链**，将需求到代码的全过程拆解为 10 个标准化技能（Skill），通过 **多维度文档对齐**、**界面操作驱动测试**、**操作点快速定位** 和 **需求变更可回溯**，让 AI 和人类在同一个框架下高效协作。

---

## 🎯 核心理念

```
需求/代码分析 → magic-1-tech-design → magic-2-module-design → magic-3-test-operation
                                                                          ↓
                                                              ┌───────────┘
                                                              ↓
                                                     magic-4-database-schema
                                                              ↓
                                                      magic-5-api-spec
                                                              ↓
                                               ┌──────────────┴──────────────┐
                                               ↓                              ↓
                                      magic-6-code-impl  ←──  magic-7-req-change
                                               ↓
                                         magic-8-phenomenon
                                         现象诊断与修复
                                               ↑
                    ┌──────────────────────────┬──────────────────────────────┐
                    ↓                          ↓                              ↓
            sp-1-mvplogic              sp-2-bughunter                 sp-3-frontend-design
            新需求讨论                  AI代码Bug扫描                    前端视觉设计
```

**五个文档（1~5）只生成一次**，后续迭代都通过 `/magic-6-code-impl`（编码实现）和 `/magic-7-req-change`（需求变更）两个技能持续演进，代码实现后由 `/magic-8-phenomenon` 诊断用户反馈的界面问题。新需求点通过 `/sp-1-mvplogic` 互动讨论理清逻辑，AI 生成代码后通过 `/sp-2-bughunter` 扫描 AI 专属 bug，通过 `/sp-3-frontend-design` 优化前端 UI 美观度。

## 🔥 三大亮点

### 1. 多维度对齐

传统开发中，需求、设计、代码、测试是四张皮。Magic-Spec 通过 **五层文档的逐级引用和双向联动** 强制对齐：

| 维度 | 产出文档 | 对齐方式 |
|------|---------|----------|
| 🏗️ 技术方案 | `magic-1-tech-design` | T-XX 方案编号贯穿所有文档 |
| 📦 模块设计 | `magic-2-module-design` | M-XX 模块编号，后端 `M-XX-01~09` + 前端 `M-XX-10+` |
| 🧪 操作流程 | `magic-3-test-operation` | OP 操作编号精确到步骤，标注"代码实现"状态 |
| 🗄️ 数据库 | `magic-4-database-schema` | 表结构从 OP 的真实 SQL 中提取，不凭空设计 |
| 🔌 API 接口 | `magic-5-api-spec` | 接口从 OP 的后端逻辑中提取，字段从表结构映射 |

**对齐链路**：
```
T-01 方案 → M-01 模块 → OP-1.1.1 操作步骤 → INSERT INTO agent (...) → POST /api/agents
    ↑_______________┴_______________┴_______________┴_______________↓
                        任意节点可双向追溯
```

每个文档生成前会 **检查上游文档的确认状态**，存在"待确认"项则强制中断并逐项向用户确认，杜绝"假对齐"。

---

### 2. 界面操作驱动，测试先行

不写抽象的"用户故事"或模糊的"验收标准"。**直接按界面操作步骤写测试文档**，人类测试人员拿起来就能执行：

```
> 编号：OP-3.1.1
> 步骤：1
> 导航路径：设置 tab → 服务器管理页面 → 新增弹窗
> 操作：
>   - 点击"新增"按钮
>   - 填写名称"测试数据"
>   - 选择关联项"选项A"
>   - 状态设为"启用"
>   - 点击"保存"
> 后端逻辑：
>   1. T-02 接收 POST /api/records，校验请求参数
>   2. 校验 name 不为空且不重复，校验关联字段不为空
>   3. 开启事务：INSERT INTO main_table (name, status)
>   4. 写入关联表：INSERT INTO relation_table (main_id, ref_id)
>   5. 提交事务，返回新建记录 ID
> 代码实现：未实现
```

**三类操作全覆盖**：
- 🖥️ **管理后台操作** — Web 页面的增删改查、配置等
- 📱 **外部应用操作** — 企业微信/钉钉等外部入口
- ⏰ **系统自动行为** — 定时任务、状态联动、回调等

每个操作步骤只描述 **影响后端的动作**（纯前端校验、弹窗打开等不描述），每一步都标注"代码实现"状态（`未实现` / `已实现`），进度一目了然。

---

### 3. 出现问题，OP 编号快速定位

这是 Magic-Spec 最实用的日常价值。线上出问题时：

```
用户投诉："标签管理页新增标签后列表没刷新"

传统排查：翻需求文档 → 找设计文档 → 搜代码 → 猜 API → 查日志
Magic-Spec：OP-3.1.1 → 直接定位到"操作步骤"和"后端逻辑"
```

通过 **OP 编号（如 OP-3.1.1）** 可以：

| 追溯目标 | 路径 |
|----------|------|
| 期望行为是什么 | → 文档 3 的对应 OP 步骤"操作"列 |
| 后端应该执行什么逻辑 | → 文档 3 的对应 OP 步骤"后端逻辑"列 |
| 涉及哪张表 | → 文档 4 的对应表结构 |
| 调用哪个 API | → 文档 5 的对应接口 |
| 谁实现的、什么时候 | → 文档顶部的"变更记录" |
| 是否已实现 | → 文档 3 的"代码实现"列 |

**不需要翻遍需求文档、设计文档、代码仓库、日志系统**。OP 编号就是你的单向溯源码。

## 🗺️ 技能全景图

### 一次性生成（1~5）：从需求到完整设计文档链

| 命令 | 核心产出 | 前置依赖 |
|------|---------|---------|
| `/magic-1-tech-design` | 技术方案：T-XX 方案拆分、技术栈选型、目录结构 | 需求文档 或 现有代码 |
| `/magic-2-module-design` | 模块详细设计：M-XX 模块、功能点拆解、工时评估 | 文档 1 |
| `/magic-3-test-operation` | 测试操作文档：OP 步骤、导航路径、后端逻辑 | 文档 1、2 |
| `/magic-4-database-schema` | 数据库结构：表字段、索引、ER 关系图 | 文档 1、2、3 |
| `/magic-5-api-spec` | API 接口文档：路径、参数、响应、错误码 | 文档 1、2、3、4 |

> 📌 **1~5 文档只生成一次**。不是"每次变更都重做"，而是生成后作为项目的 **持久化规格基准**。

### 持续迭代（6~7）：编码 + 变更

| 命令 | 核心能力 | 工作方式 |
|------|---------|---------|
| `/magic-6-code-impl` | 逐功能实现代码 | 每次一个 OP 步骤 → 前端先设计计划 → 后端先写测试 → 前后端一起实现 → 更新文档状态 |
| `/magic-7-req-change` | 需求变更管理 | 分配 CHG-XXX 编号 → 五维度深度讨论 → 更新受影响文档 → 代码标记"未实现" |
| `/magic-8-phenomenon` | 界面现象诊断 | 用户描述界面问题 → 三层诊断 → 明确告知问题类型 → 对应处理 |

**亮点**：
- `/magic-6-code-impl` 前端采用 **设计驱动**：实现前先制定设计计划（色彩、字体、布局、签名元素），评审独特性后再编码。每个页面应有独特的视觉识别，不套模板
- `/magic-6-code-impl` 后端采用 **先编码后测试**：先实现代码，再编写测试验证正确性，确保核心逻辑被覆盖
- `/magic-6-code-impl` 实现前 **自动分析代码变更是否影响设计文档**，有影响先更新文档再编码
- `/magic-7-req-change` 在更新文档前进行 **五维度深度讨论**（背景动机 → 前端设计 → 影响面 → 风险 → 替代方案），提前暴露问题
- `/magic-8-phenomenon` **明确告知问题类型**：使用方式问题 / Bug / 文档问题，用户不用猜
- `/magic-8-phenomenon` **文档问题需用户确认**：展示变更计划 → 用户确认 → 只改文档，不改代码。代码由用户自行通过 magic-6-code-impl 实现
- `/magic-7-req-change` 分配 **CHG-XXX 变更编号**，贯穿所有受影响文档，`/magic-6-code-impl` 实现后回写 `代码：已实现`

### 自由讨论（sp-1）：新需求孵化器

| 命令 | 核心能力 |
|------|---------|
| `/sp-1-mvplogic` | 互动式讨论某个需求的实现逻辑 |

**与众不同**：`/sp-1-mvplogic` 不套模板、不填框架，而是盯着用户提供的内容（一张表、一段代码、一句话需求）**深挖细节、发现用户自己没注意到的问题**。核心原则：**不假设，只询问**——不知道数据量级就问，不确定字段含义就问，不清楚业务规则就问，绝不用假设数据推进讨论：

- "你这个表 1000 万行，按你提的 5 分钟全量同步，根本跑不完"
- "`parent_id` 默认值 `10000000` 是什么含义？这可能影响你的同步逻辑"
- "软删除的记录同步不同步？不同步的话关联数据会断裂"

### Bug 扫描（sp-2）：AI 代码专属猎手

| 命令 | 核心能力 |
|------|---------|
| `/sp-2-bughunter` | 扫描 AI 生成代码中的专属 bug，只报告不修改 |

**为什么需要它**：AI 生成的代码和人类写的代码，bug 类型完全不同。人类容易出空指针、边界条件；AI 容易出 **兜底掩盖真问题**、**假设性代码**、**happy-path-only**。普通 code review 按人类思维找 bug，AI 的这类问题极易漏掉。

**六种 AI 专属 bug 模式**：

| 模式 | 典型症状 | 为什么危险 |
|------|---------|-----------|
| 🎭 **兜底掩盖** | `data?.name ?? ''`、空 catch、静默 return | 真实的数据错误被悄悄吞掉，等发现时数据已丢三个月 |
| 🤔 **假设性代码** | 字段名猜错、类型猜错、业务规则猜错 | 页面不报错但显示的是错的数据 |
| 🟢 **Happy-Path Only** | 无 loading/empty/error 态、无事务回滚、无幂等 | 正常流程跑得通，一有异常就出问题 |
| 🎈 **虚假完整性** | stub 函数、假校验、假权限、假分页 | 代码看起来什么都有，实际什么都没做 |
| 🔀 **前后端脱节** | 字段名不一致、类型不一致、分页格式不一致 | 前端和后端各说各话，联调时才发现不匹配 |
| 💀 **死代码** | 未用 import、未调用函数、僵尸代码路径 | 增加维护成本，且两处定义可能已不同步 |

### 现象诊断（8）：界面问题自动诊断

| 命令 | 核心能力 |
|------|---------|
| `/magic-8-phenomenon` | 用户描述界面不符合预期的现象，AI 按三层链路诊断，明确告知问题类型 |

**解决什么问题**：界面上某个功能"不对劲"（点了没反应、数据不对、流程走不通），但不清楚到底是 Bug、自己操作错了、还是文档写错了。传统做法是"先提单、再排查、再修复"，周期长。

**三层诊断 + 明确告知**：

```
用户描述现象 → 第 1 层：用户使用方式对不对？
                ├─ 不对 → "诊断结论：使用方式问题" → 告知正确用法
                └─ 对   → 第 2 层：文档和代码谁错了？
                           ├─ 文档对，代码错 → "诊断结论：这是一个 Bug" → 直接修复代码
                           └─ 文档错 → "诊断结论：文档问题" → 展示变更计划
                                            → 用户确认 → 只改文档，不改代码
                                            → 用户自行运行 magic-6-code-impl 实现代码
```

**三种处理方式**：

| 诊断结果 | AI 做什么 | 需要用户确认？ |
|---------|----------|--------------|
| **使用方式问题** | 告知正确操作，不改任何东西 | 否 |
| **Bug（文档正确）** | 直接修复代码，不改文档 | 否 |
| **文档问题** | 展示计划 → 用户确认 → 只改文档，不改代码 | **是** |

### 前端设计（sp-3）：即时 UI 美化

| 命令 | 核心能力 |
|------|---------|
| `/sp-3-frontend-design` | 用户提出页面美观问题，AI 评估后直接修改代码 |

**解决什么问题**：开发过程中 UI 往往"能用就行"——颜色硬编码、间距随意、用 emoji 当图标、空状态空白一片。报给设计师要排队，自己改又不知道好看的标准。

**直接修改代码，不输出文档**：

```
用户说"这个页面不好看" → AI 读取代码 → 视觉问题清单评估
→ 直接修改代码（Token 统一 / emoji 替换 / 间距对齐 / 布局优化）
→ 自检确认 → 完成
```

**五大自动修正项**：

| 修正项 | 说明 |
|-------|------|
| ① Token 统一 | 新增/继承 CSS 变量，替代所有硬编码色值 |
| ② emoji 替换 | **全局搜索替换**：`⚙️✏️🗑️➕✅` → Lucide SVG 图标 |
| ③ 间距对齐 | 所有 padding/margin/gap 修正为 4px 倍数 |
| ④ 布局呼吸感 | 增加间距、行高、内边距，让页面不拥挤 |
| ⑤ 状态补充 | 空状态/加载态/错误态最低要求达标 |

**硬性红线**：

- ❌ **禁止 emoji 图标** — 全部替换为 Lucide 或对应框架 SVG
- ❌ **禁止硬编码色值** — 全部通过 CSS 变量引用
- ❌ **禁止"暂无数据"** — 空状态必须有引导操作

## 🎭 更多使用场景

### 场景一：重构老旧项目

```
没有需求文档的老项目 → /magic-1-tech-design（代码分析模式）
→ 逆向推导技术方案 → 逐技能生成完整文档链 → 基于文档安全重构
```

### 场景二：从零启动新项目

```
PRD/需求文档 → /magic-1-tech-design（文档模式）→ /magic-2-module-design
→ /magic-3-test-operation → /magic-4-database-schema → /magic-5-api-spec
```

### 场景三：需求变更不凌乱

```
需求变更 → /magic-7-req-change → CHG-XXX 编号分配 → 五维度讨论
→ 受影响文档自动更新 + 变更记录 → /magic-6-code-impl 按 CHG-XXX 实现代码
```

### 场景四：设计决策可回溯

```
"这个字段为什么设计成 TEXT 而不是 VARCHAR？"
→ 文档 4 的变更记录 → CHG-015 → 文档 1~5 中该编号的讨论结论 → 当时的权衡有据可查
```

### 场景五：多人协作的任务拆分

```
文档 1 的 T-XX 方案 → 独立工作包 → 分配给不同开发者
文档 2 给出每个模块的工时评估和依赖关系 → 自动排出开发迭代计划

```

## 🚀 安装：加载技能到你的编码助手

Magic-Spec 是一组 **Skill 文件**（每个子目录下的 `SKILL.md`），需要安装到编码助手的 skills 目录下才能通过斜杠命令调用。支持以下编码助手：

| 编码助手 | Skills 目录 | 安装方式 |
|----------|------------|---------|
| **Claude Code** | `.claude/skills/` | 复制技能文件夹到该目录 |
| **Codex** | `.codex/skills/` | 同上 |
| **Trae** | `.trae/skills/` | 同上 |
| **OpenCode** | `.opencode/skills/` | 同上 |

### 安装命令

```bash
# 在项目根目录执行，将所有技能文件夹复制到 Claude Code（以 Claude Code 为例）
mkdir -p .claude/skills

cp -r 1-tech-implementation-plan .claude/skills/magic-1-tech-design
cp -r 2-detailed-design        .claude/skills/magic-2-module-design
cp -r 3-operation-flow         .claude/skills/magic-3-test-operation
cp -r 4-database-schema        .claude/skills/magic-4-database-schema
cp -r 5-api-spec               .claude/skills/magic-5-api-spec
cp -r 6-code-impl              .claude/skills/magic-6-code-impl
cp -r 7-req-change             .claude/skills/magic-7-req-change
cp -r sp-1-mvplogic            .claude/skills/sp-1-mvplogic
cp -r sp-2-bughunter           .claude/skills/sp-2-bughunter
cp -r sp-3-frontend-design     .claude/skills/sp-3-frontend-design
cp -r 8-phenomenon             .claude/skills/magic-8-phenomenon
```

> 💡 不同编码助手的安装目录只差前缀：`.claude/` → `.codex/` → `.trae/` → `.opencode/`，安装命令如法炮制即可。

## ⚡ 使用方式

安装完成后，通过 `/` 斜杠命令调用技能（命令名 = SKILL.md 中 `name:` 字段的值）。

### 启动新项目

```bash
# 第一步：设计技术方案（二选一）
/magic-1-tech-design            # 传入 PRD/需求文档，从零设计方案
/magic-1-tech-design            # 不传文档，分析现有项目代码反向推导方案

# 第二步：生成设计文档链（1→5 逐级生成，每个只做一次）
```

## 🔧 设计原则

| 原则 | 说明 |
|------|------|
| **文档优先于代码** | 先改文档，后写代码。文档是唯一事实来源 |
| **逐维度确认** | 不生成大量"待确认"让用户自己改，而是逐项主动询问 |
| **上游检查** | 每个技能生成前检查前置文档的确认状态，存在"待确认"则中断 |
| **变更可追溯** | CHG-XXX 编号贯穿所有文档，每次修改都有据可查 |
| **一次只做一个** | 编码实现时每次只做一个 OP 步骤，前后端一起，不批量 |
| **TDD 强制** | 先写测试确认失败，再实现代码直到通过，不做无测试的代码 |
| **最小实现** | 前端默认最小可用，不纠结 UI 细节 |
| **数据驱动** | 表结构从实际操作 SQL 中提取，API 从操作流程中提取，不做凭空设计 |
