专门查找 AI 生成代码中独有的、人类 Code Review 容易漏掉的 bug。不是通用 code review，而是盯着 AI 的思维盲区找问题。

---

**输入**：用户指定要扫描的文件、目录、或最近的变更范围。不指定则扫描当前项目所有源码文件。

**输出**：Bug 报告（Markdown），写入 `magic-align-spec/sp-2-bughunter/` 目录下：

```
magic-align-spec/sp-2-bughunter/
├── overview.md                  # 扫描记录索引
└── <日期>-<范围>.md              # 单次扫描报告
```

---

## 执行步骤

### 1. 确定扫描范围

向用户确认扫描范围：
- 如果不指定，默认扫描当前项目的 `src/`、`app/`、`pages/`、`components/`、`api/` 等源码目录
- 如果用户指定了文件或目录，只扫描指定范围
- 如果项目有 `magic-align-spec/` 目录，优先扫描与最近变更相关的代码

### 2. 逐文件扫描

对每个文件，按以下 **AI 专属 bug 模式** 逐项检查。不是找通用 bug（如空指针、类型错误），只找 AI 特有的问题。

#### 模式一：AI 兜底掩盖真问题

AI 生成的代码常常加上看似"健壮"的兜底逻辑，实际是"不可见 bug 制造机"：

- **空值兜底**：`data?.name ?? ''`、`list || []`、`value ?? defaultValue` — 兜底让页面不报错，但也让真实的数据缺失永远不被发现。数据没有返回 -> 页面静默显示空 -> 三个月后才发现数据丢了
- **异常吞噬**：`try { ... } catch { /* 空 */ }`、`try { ... } catch { return null }` — 异常被吞了，上层完全不知道出过问题。调用方拿到 null 以为是正常返回值
- **静默降级**：`if (!data) return`（函数什么都不做就退出了）、`if (error) return <Empty />`（用户看到空白页但不知道出错了）
- **重复调用防抖缺失**：AI 生成的 onClick/onChange 没有防抖，用户快速连点导致重复提交、重复写入

**检查要点**：每一个兜底、每一个 catch、每一个提前 return，都要追问——这里出了问题，外面能感知到吗？

#### 模式二：AI 的假设性代码

AI 填代码时靠推测补全，推测错误就出 bug：

- **字段名假设**：前端用了 `data.userName`，后端返回的是 `data.username`（大小写不一致）；或者前端直接用了后端字段，但后端字段改了名
- **数据结构假设**：AI 假设 API 返回 `{ list: [...] }`，实际返回 `{ data: { items: [...] } }`；假设关联数据已经 eager load 了，实际是懒加载
- **类型假设**：AI 假设某个值是 string，实际后端返回 number；假设 status 值是 `'active'/'inactive'`，实际是 `1/0`
- **环境假设**：AI 假设有某个全局变量（`window.__INITIAL_STATE__`）、假设某个库已经注入（`$http`）、假设某个环境变量存在
- **业务规则假设**：AI 假设"名称不可重复"但实际业务允许重名；AI 假设"删除前需要二次确认"但实际有回收站机制不需要

**检查要点**：每个 AI 写的字段访问、类型转换、业务判断，对照实际的数据结构、API 文档、业务规则核实。

#### 模式三：Happy-Path Only

AI 的默认思维方式是"先让正常流程跑通"，异常路径留给你自己发现：

- **后端无事务回滚**：创建订单成功了，扣库存失败了 -> 订单没回滚
- **后端无幂等**：网络重试导致同一请求被执行两次 -> 重复创建记录
- **前端无 loading 态**：按钮点击后没有 loading，用户可以连点 -> 重复提交
- **前端无 empty 态**：列表为空时页面空白，用户不知道是没数据还是加载中还是出错了
- **前端无 error 态**：API 调用失败后没有错误提示，用户操作了但不知道操作有没有生效
- **并发无锁**：AI 写了一个"读-改-写"逻辑，没考虑并发场景下的数据一致性问题

**检查要点**：找到每个核心操作，检查失败路径、重复操作、边界状态是否都有处理。

#### 模式四：虚假的完整性

AI 生成的代码看起来完整（有类型、有注释、有 import、有导出），但实质是空壳：

- **stub 函数**：函数体只有 `return {}`、`return []`、`// TODO`、`pass`，但调用方已经在用了
- **假校验**：`if (!name) throw Error('name required')` 写了，但没有在路由层或 controller 层调用
- **假权限**：注释了 `// TODO: check permission`，但没有实现
- **假分页**：API 接受 page/pageSize 参数但返回全量数据
- **假错误处理**：写了 `onError` 回调但从来没传过；定义了错误码常量但代码里全用字符串

**检查要点**：每个看起来已经实现了的功能，找到它的调用方/消费方，确认真的在跑。

#### 模式五：前后端脱节

AI 前后端分开生成，导致两边对不上：

- **字段名不一致**：前端发 `{ userName, emailAddr }`，后端期望 `{ username, email }`
- **类型不一致**：前端发 `status: "enabled"`（string），后端期望 `status: 1`（integer）
- **校验不一致**：前端校验允许空值，后端拒绝空值；前端允许 200 字，后端限制 100 字
- **枚举值不一致**：前端下拉框有"启用/停用/草稿"，后端只接受 "active/inactive"
- **分页格式不一致**：前端发 `{ page: 1, size: 20 }`，后端期望 `{ offset: 0, limit: 20 }`

**检查要点**：对比前端 API 调用和后端 API 定义的参数名、类型、枚举值、分页格式。

#### 模式六：AI 生成的死代码

AI 生成代码时喜欢"多生成一点"，导致死代码残留：

- **未使用的 import**：引入了但没用到，或者曾经用到但被后续编辑删了引用
- **未调用的函数**：定义了 helper/工具函数，但没有任何地方调用
- **未使用的状态**：useState 定义了但从未 set；或者 set 了但从未被读取
- **冗余的类型定义**：前后端各定义了一份相同的类型，但两边已经不一致了
- **僵尸代码路径**：`if (false)`、`if (env === 'never-happens')`、永远不成立的 switch case

**检查要点**：每个定义检查是否有消费方，每个 import 检查是否被使用。

### 3. 输出扫描报告

每条发现单独记录，格式：

```markdown
# Bug 扫描报告 — {范围}

**扫描日期**：{日期}
**扫描范围**：{文件列表或目录}

---

## 发现总览

| 编号 | 模式 | 严重程度 | 文件 | 问题摘要 |
|------|------|---------|------|---------|
| BUG-01 | 兜底掩盖 | 🔴 高 | src/api/user.ts:42 | catch 块为空，API 失败无感知 |
| BUG-02 | 假设性 | 🟡 中 | src/pages/list.tsx:58 | 假设 API 返回 .list 字段 |
| ... | | | | |

---

## 详细发现

### BUG-01：{问题标题}

**文件**：`src/api/user.ts:42`
**模式**：兜底掩盖 — 异常吞噬
**严重程度**：🔴 高

**问题代码**：
```typescript
try {
  const data = await fetchUser(id)
} catch {
  // 什么都不做
}
```

**问题描述**：
fetchUser 失败时异常被完全吞掉，调用方收到 undefined，页面静默不显示用户数据。用户看到空白卡片但不知道为什么。

**潜在影响**：
- 生产环境 API 偶发 500 -> 用户看不到自己的数据 -> 投诉"系统坏了"但运维查不到任何错误日志
- 如果这个用户数据用于权限判断，可能导致权限绕过

**建议方向**：
- catch 中至少打错误日志
- 向上抛出或返回明确的错误状态给 UI 层展示
```

## 编写原则

- **只找 AI 特有的 bug**：不找通用代码问题（如命名不规范、缺少注释、函数太长），只找 AI 思维盲区产生的问题
- **只报告不修改**：本 skill 的职责是发现和报告 bug，不修改任何代码。修复交给 `/magic-6-code-impl` 或人工处理
- **不假设，要核实**：发现可疑代码时，不假设它是 bug，而是对比前后端代码、API 文档、需求文档来确认
- **每条发现给严重程度**：🔴 高（生产事故级）/ 🟡 中（功能异常）/ 🟢 低（代码质量），帮助排优先级
- **给出具体行号和代码片段**：不说"某处有个问题"，精确到文件和行号，引用原始代码
- **独立运作**：不依赖其他 skill 的产出，直接扫描代码文件
- **不把 AI 做的东西当成对的**：不要因为是 AI 生成的代码就有"信任假设"，发现可疑就标记
