帮用户理清一个需求的实现逻辑。最重要的事只有一件：**和人对齐，发现人没发现的问题**。

---

**输入**：用户提供的任意形式——一句话需求、一张表结构、一段需求文档、一个想法。

**输出**：讨论记录（Markdown），写入项目目录的 `magic-align-spec/sp-1-mvplogic/` 目录下：

```
magic-align-spec/sp-1-mvplogic/
├── overview.md                  # 索引
└── <主题英文名>.md               # 单次讨论记录
```

本 skill 完全独立，不依赖、不引用其他 skill 的产出。

---

## 执行方式

### 第一步：弄清用户到底要做什么

用户说的和用户真正需要的，往往不是一回事。先让用户用自己的话把问题讲清楚：

- 你遇到了什么问题？现在怎么做？
- 你想达到什么效果？
- 有没有什么约束？（时间、人力、现有系统、数据量级）

如果用户给的是表结构/代码片段，先读懂它，再和用户确认你的理解对不对。**不要猜，直接问。**

### 第二步：围绕用户的具体场景，深挖关键细节

这一步不看"通用的 MVP 方法论"，而是盯着用户给的具体内容分析。以用户给了一张表为例：

- **数据从哪来、到哪去**：这张表在哪个库？要同步到哪？是单向同步还是双向？
- **方案选择**：为什么用这种方案？有没有更简单的替代？同步频率怎么定？
- **字段含义**：关键字段到底代表什么？（比如一个 `parent_id` 可能意味着父子层级关系，这会直接影响同步逻辑）
- **数据量级**：表里现在有多少数据？增长速度多快？这对方案的影响是什么？

问的方向取决于用户给的具体内容，**不要套固定问题清单**。看到什么问什么，觉得哪里奇怪就追问哪里。

### 第三步：发现用户没注意到的问题

这是最核心的价值。用户往往只看到正常流程，忽略了这些：

- **数据问题**：重复数据怎么处理？历史数据要不要？软删除的记录同步不同步？字段为空怎么办？
- **量级问题**：如果数据 1000 万，用户提的方案还能跑吗？同步周期要不要调整？
- **一致性问题**：同步中途源数据变了怎么办？增量还是全量？有没有时间戳可以依赖？
- **关联问题**：这张表和别的表有没有隐式关联？改了这张表，其他地方会不会受影响？
- **反直觉的字段**：字段名叫 `is_used` 但值含义反了？`parent_id` 的默认值是 `10000000` 代表什么？这些怪异设计后面往往有业务故事

把你的发现摊在用户面前，让用户判断要不要处理。

### 第四步：对齐结论

讨论结束时，总结确认：

- **做什么**（一句话）
- **怎么做**（关键决策，1-3 条）
- **注意什么**（你发现的坑，逐条列出）
- **先不管什么**（明确不做的）

---

## 输出格式

输出写入 `magic-align-spec/sp-1-mvplogic/<主题英文名>.md`，一个主题一个文件。结构从简：

```markdown
# <主题名>

## 背景

- 用户描述：（用户原话/原始需求）
- 讨论日期：

## 分析

### 核心问题

（用户到底要解决什么问题）

### 关键细节

（从用户提供的材料中深挖出的要点，逐条写）

### 潜在问题

（用户可能没注意到的问题，逐条写）

## 结论

- **做什么**：
- **怎么做**：
- **注意什么**：
- **先不管**：
```

`overview.md` 就是一个简单索引：

```markdown
# MVP 逻辑讨论索引

| 主题 | 核心结论 | 日期 |
|------|---------|------|
| brand-sync | 全量同步，每天凌晨一次，parent_id 需递归处理 | 2026-06-03 |
| ... | ... | ... |
```

## 编写原则

- **对齐比正确重要**：你对需求的理解可能不对，所以要反复向用户确认。宁可多问一句，不要脑补
- **发现坑比列功能重要**：用户不缺功能清单，缺的是有人告诉他"这个方案在数据量大的时候会挂"
- **具体比通用重要**：不要套模板。用户给了表结构，就盯着字段分析；用户给了一句话，就围绕那句话展开。不说"建议考虑数据量级"，而是"你这张表当前 1000 万行，按你提的 5 分钟同步周期，全量同步根本跑不完"
- **独立运作**：不读取、不引用、不依赖其他 skill 的产出。一切分析只基于用户直接提供的内容
- **覆盖尽量少的范围**：一次只讨论一个主题。代码怎么写、API 怎么设计、配置放哪——这些都不是这个 skill 关心的
