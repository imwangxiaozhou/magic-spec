基于操作流程文档和数据库表结构文档，提取并整理所有 REST API 接口，生成一份完整的 API 接口文档。

---

**前置条件**：
- `magic-align-spec/3-operation-flow/overview.md` 必须已生成
- `magic-align-spec/4-database-schema/overview.md` 必须已生成

**输入**：
- 操作流程文档：提取所有 API 端点（路径、方法、调用逻辑）
- 数据库表结构文档：映射请求参数和响应字段的类型、约束、枚举值

**输出**：API 接口文档（Markdown 格式），按模块拆分为多个文件，写入当前项目目录的 `magic-align-spec/5-api-spec/` 目录下：

```
magic-align-spec/5-api-spec/
├── overview.md              # 文档信息、接口总览表、通用规范（分页、响应格式、错误码）
├── M-01-<模块名>-api.md     # 对应模块的所有 API 接口详细设计
├── M-02-<模块名>-api.md
└── ...
```

- `overview.md` 包含接口总览表和通用规范（分页参数、响应格式、通用错误码）
- 每个 `M-XX-<模块名>-api.md` 包含该模块的所有 API 接口详细设计（路径、参数、响应、错误码）

---

## 执行步骤

### 1. 前置检查

依次检查两份前置文档，缺失则告知用户先生成对应文档。

### 2. 技术方案确认状态检查

读取 `magic-align-spec/1-tech-implementation-plan/` 目录下 overview.md 中每个技术方案（T-XX）的"确认状态"字段：

- **全部已确认**：正常继续
- **存在待确认或存疑的方案**：使用 **AskUserQuestion** 逐项向用户确认，根据回复更新 `magic-align-spec/1-tech-implementation-plan/` 目录下对应方案文件的确认状态
- 确认完成后继续执行

### 3. 提取接口列表

从操作流程文档的"后端影响"列中提取所有 API 端点：

- 接口路径和方法（GET/POST/PUT/DELETE）
- 调用逻辑（校验规则、事务操作、数据变更）
- 按数据表模块和服务模块归类

### 4. 映射请求/响应字段

从数据库表结构文档中，为每个接口映射：

- **请求参数**：从表的字段约束中提取必填/选填、类型、长度限制
- **响应字段**：从表结构映射返回的字段列表和嵌套关系
- **枚举值**：从 status 等字段的约束中提取可选值

### 5. 输出

将文档按模块拆分为多个文件，写入 `magic-align-spec/5-api-spec/` 目录：

1. 先写 `overview.md`，包含文档信息、接口总览表、通用规范（分页、响应格式、错误码）
2. 再逐模块写 `M-XX-<模块名>-api.md`，每个文件包含该模块的所有 API 接口详细设计

## 文档框架

### overview.md

#### 1. 文档信息

| 字段 | 值 |
|------|-----|
| 项目名称 | （继承自 tech-implementation-plan） |
| 文档版本 | |
| 创建日期 | |
| 前置文档 | magic-align-spec/3-operation-flow/overview.md, magic-align-spec/4-database-schema/overview.md |
| 评审状态 | 草稿 / 评审中 / 已通过 |

#### 2. 接口总览

按模块列出所有接口：

| 编号 | 模块 | 接口路径 | 方法 | 说明 | 详细文件 |
|------|------|---------|------|------|---------|
| API-01 | 岗位标签 | /api/post-tags | GET | 分页查询标签列表 | M-04-post-tag-api.md |
| API-02 | 岗位标签 | /api/post-tags | POST | 新增标签 | M-04-post-tag-api.md |
| ... | | | | | |

#### 3. 通用规范

##### 3.1 分页参数

| 参数名 | 位置 | 类型 | 必填 | 默认值 | 说明 |
|--------|------|------|------|--------|------|
| page | query | integer | 否 | 1 | 页码 |
| page_size | query | integer | 否 | 20 | 每页条数，最大 100 |

##### 3.2 通用响应格式

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "pagination": {
    "page": 1,
    "page_size": 20,
    "total": 100
  }
}
```

##### 3.3 通用错误码

| 错误码 | 说明 |
|--------|------|
| 0 | 成功 |
| 400 | 请求参数错误 |
| 401 | 未登录 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 409 | 数据冲突（如唯一键重复） |
| 500 | 服务器内部错误 |

### M-XX-<模块名>-api.md（每模块一个文件）

每个接口按以下结构编写：

#### API-XX：接口名称

**基本信息**：

| 字段 | 值 |
|------|-----|
| 路径 | /api/xxx |
| 方法 | GET / POST / PUT / DELETE |
| 关联模块 | M-XX |
| 关联技术方案 | T-XX |

**功能说明**：一句话描述接口用途

**请求参数**：

| 参数名 | 位置 | 类型 | 必填 | 说明 |
|--------|------|------|------|------|
| name | body | string | 是 | 名称，最多 50 字 |
| status | body | string | 否 | 状态，可选值：enabled / disabled |

**请求示例**：

```json
{
  "name": "示例名称",
  "status": "enabled"
}
```

**响应字段**：

| 字段名 | 类型 | 说明 |
|--------|------|------|
| id | UUID | 唯一标识 |
| name | string | 名称 |
| created_at | string | 创建时间 |

**响应示例**：

```json
{
  "code": 0,
  "data": {
    "id": "xxx",
    "name": "示例名称",
    "created_at": "2026-05-28T10:00:00Z"
  }
}
```

**调用逻辑**（继承自操作流程文档）：

1) 校验 xxx
2) 写入 xxx
3) 返回 xxx

**错误码**：

| 错误码 | 说明 |
|--------|------|
| 400 | 参数校验失败 |
| 409 | 名称重复 |
| 404 | 资源不存在 |

## 编写原则

- **从操作流程提取接口**：接口路径和方法必须来自 operation-flow 中实际出现的内容，不凭空添加
- **从表结构映射字段**：请求参数和响应字段的类型、约束来自 database-schema，保持一致
- **调用逻辑完整**：继承 operation-flow 中的校验规则、事务操作、数据变更描述
- **编号一致**：关联模块编号（M-XX）和技术方案编号（T-XX）与前序文档保持一致
- **先管理后台后内部**：管理后台 API 详细展开，内部接口简要列出
- **按模块拆分文件**：每个 M-XX 一个独立 API 文件，overview.md 放总览和通用规范
